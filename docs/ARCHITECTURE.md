# Архитектура: условие → подготовка → дерево экспериментов

Один запуск содержит общую подготовку и ограниченное дерево экспериментов.
Нулевая нода — простой baseline, следующие гипотезы строятся по измеренным
результатам и различиям pipeline. Политика обхода пока простая; глобальный оптимум
и математическая правильность рассуждений модели не гарантируются.

Для сдачи `package_solution.py` экспортирует этот же код в плоский ZIP:
корневые `solution.py`, `alfa_*.py`, неизменённый requirements организаторов.
Только при экспорте меняются импорты и путь к worker; артефакты в ZIP не входят.
Платформа запускает `python3 solution.py task.md` и передаёт адрес / ключ прокси
через окружение. `OPENAI_MODEL` необязателен. Итог сохраняется рядом с `task.md`.

## Путь и хранение

```text
Markdown → 4 extractor’а → проверка схем / evidence → extraction.json
  → Qwen пишет prepare.py → Python читает данные → preparation.json + split.npz
  → baker предлагает план → start.json → реализатор пишет experiment.py и заметки
  → короткая проверка / исправление кода → запуск → общий scorer → finish.json
  → Python сравнивает планы / score → delta.json → Baker → пара новых нод
```

```text
artifacts/<run-id>/
├── extraction/             problem.json, data.json, metric.json, output.json
├── extraction.json         Все четыре блока с evidence
├── report.json             Статус этапа, ошибки, замечания, попытки API и usage
├── prepare.py              Общие загрузчик, split, scorer и writer от Qwen
├── preparation.json        Конфигурация и измеренные факты о данных
├── preparation.log         Диагностика исполнения подготовки
├── split.npz               Точные fit / validation индексы
├── delta.json              Общая история всех нод и текущий лидер
├── nodes/node_*/
│   ├── start.json           Исходный план Baker и контекст, до реализации
│   ├── experiment.py        Одна реализация модели
│   ├── finish.json          Статус / этап отказа, время, score, заметки, хеши плана / кода
│   ├── delta.json           Сравнения этой ноды со всеми предыдущими
│   ├── execution.log        Диагностика запуска
│   ├── validation_predictions.csv
│   └── <файл ответа>        Имя и формат из условия
└── best.json                Указатель на оценённую ноду
```

Все пути артефактов относительны каталогу запуска или ноды, как указано в
контракте. Входные файлы в preparation указаны относительно `task_directory`.
Датасеты, split и вычислитель метрики общие: в каждой ноде их не дублируем.
Генерируемые файлы исключены из git. Одноразовые диагностические прогоны удаляем
после проверки; ошибки рабочего запуска сохраняются как его результат.

## Извлечение

Четыре независимых асинхронных запроса получают только исходный Markdown:

- `problem`: тип задачи, target(s), единицы, классы и дословные оговорки.
- `data`: входные файлы, роли, произвольные имена / форматы, ID и параметры чтения.
- `metric`: основная метрика, направление, определение / формула / ссылка на код;
  дополнительные метрики отдельно. Названия метрик не ограничены перечнем.
- `output`: файлы ответа, формат, колонки, тип предсказаний и порядок строк.

`evidence[field]` — список точных цитат из исходника для заполненного поля.
Неуказанные сведения остаются `null` / пустыми коллекциями, без evidence.
Проверяем структуру JSON, отсутствие нечисловых NaN / Infinity, наличие цитат
в исходнике с нормализацией пробелов и буквальных имён в их подтверждениях.
Это подтверждение происхождения, а не доказательство правильного понимания.
Словарь цитат для вложенного поля приводится к плоскому списку; дубли и evidence
для пустого поля удаляются. Сами цитаты при этом не переписываются. Число цитат
и длина реального фрагмента не ограничены произвольными порогами старой схемы.

Здесь не проверяем доступность данных, поддержку метрики, число колонок ответа
или конкретный CSV-формат. Каждый принятый блок сохраняется по мере готовности;
после четырёх блоков Python создаёт `extraction.json` без дополнительного LLM-вызова.
Некорректный ответ получает одну попытку JSON-repair. Непринятый ответ не заменяется
заранее подготовленными фактами. Диагностика содержит поле и причину ошибки,
сырые невалидные ответы API и внутренние рассуждения не сохраняются.

## Подготовка: решения Qwen, факты из Python

Контроллер передаёт preparer’у условие, extraction и инвентаризацию имён / размеров
файлов. Qwen предлагает привязку входов, способ чтения, validation, scorer и writer.
Он возвращает конфигурацию и код, без выдуманных размеров или результатов обучения.

Общий `prepare.py` определяет четыре функции:

```python
load_data(task_directory, config)         # dict ролей → pandas.DataFrame; train / test обязательны
make_split(train, config)                 # fit и validation: целочисленные позиции строк
score(reference, predictions, config)     # scalar, основная метрика
write_submission(test, predictions, tables, config, path)  # требуемый файл ответа
```

Python выполняет загрузку, измеряет строки / колонки / типы / пропуски, проверяет
непересекающийся split и сохраняет индексы / хеши входов. Эти наблюдения вместе
с конфигурацией образуют `preparation.json`. Он не заполняется целиком словами LLM.
Пример структуры (профиль сокращён; выбор 90/10 приведён для иллюстрации):

```json
{
  "schema_version": 2, "status": "ready", "extraction": "extraction.json",
  "task_directory": "/path/to/dataset",
  "rationale": "Почему выбраны такое чтение, validation и scorer",
  "data": {"files": {"train": "learning.tsv", "test": "query.jsonl"},
           "target_columns": ["target"], "id_columns": ["record_id"]},
  "validation": {"strategy": "holdout", "test_size": 0.1, "random_state": 42,
                 "split_file": "split.npz", "fit_rows": 90, "validation_rows": 10,
                 "split_sha256": "<реальный хеш split>"},
  "metric": {"name": "custom_score", "direction": "minimize",
             "definition": "Формула из условия", "status": "ready"},
  "output": {"filename": "answer.tsv", "format": "TSV", "columns": ["record_id", "prediction"]},
  "profile": {"train": {"rows": 100, "columns": {"target": {"dtype": "float64", "missing": 0, "distinct": 80}}}},
  "source_hashes": {"learning.tsv": "<реальный хеш файла>"},
  "code_sha256": "<реальный хеш prepare.py>", "issues": []
}
```

Validation выбирается с учётом условия / структуры данных. В контроллере не зашиты
80/20, публичные имена target или набор метрик. Ошибка исполнения возвращается
Qwen для одной попытки исправления подготовки. Сырые строки таблиц в API специально
не отправляются: передаются имена / размеры, профили, требования и код.

Текущий общий интерфейс оперирует таблицами pandas. Новый файловый формат может
прочитать сгенерированный загрузчик в рамках установленных библиотек. Другие
модальности / недоступные зависимости могут потребовать расширения исполнителя;
это ограничение не делает извлечённый Markdown невалидным. Непрочитанные данные
дают blocked / ошибку подготовки с причиной, без фиктивного профиля.

Кастомная метрика реализуется в общем `prepare.py` по определению из условия.
Если определения недостаточно, её status — `needs_implementation`; score остаётся
`null`. При пригодных входах всё равно можно получить предсказания. Для всех нод
используется один scorer и один split; при их изменении нужен новый запуск.
Общие [ограничения кейса](TASK_BRIEF.md) учитываются отдельно от фактов task.md.

## План → start → реализация

Baker получает исходное условие, extraction, preparation и версии установленных ML-библиотек.
Предлагает простейший baseline: при подходящей задаче среднее, частый класс или
априорные вероятности. План содержит четыре блока: data / preprocessing / model /
training. Схема фиксирует блоки, но не перечисляет допустимые алгоритмы и параметры.

Рабочий baseline — обязательный барьер перед поиском: его finish должен иметь
status=completed без evaluation_status=failed. При отказе после исправлений поиск
останавливается с stop_reason=baseline_failed; общий дедлайн даёт time_budget.
Ноды node_001 и далее не создаются. Неописанная / нереализованная метрика со статусом
unavailable не запрещает получить предсказания; score остаётся null.

Контроллер сразу сохраняет гипотезу Baker в `start.json`. Это задание, которое
существует до первого запроса к реализатору и не меняется при исправлении кода.
Общие данные не копируются в ноду: start содержит ссылки / хеши preparation,
extraction и исходного Markdown, ссылку на prepare.py и версии библиотек.
Хеш prepare.py уже входит в preparation. Код модели ещё не существует, поэтому
его SHA-256 записывается в finish, а не в start.

Реализатор получает сохранённый start, исходное условие, preparation, prepare.py
как справочник общего scorer / writer и версии библиотек. Extraction повторно не
дублируется. runtime_contract явно описывает вход: fit содержит все колонки train,
включая признаки и targets, validation передаётся без targets, test — в исходном
порядке. Число строк берётся из измеренного профиля и фиксированного split;
smoke использует не более 200 / 50 / 50 строк fit / validation / test.
Имена, типы, missing и distinct доступны в preparation.profile; для ячеек,
кардинальность которых вычислить нельзя, distinct=null. Сырые строки не передаются.
Родитель представлен только parent_reference с node_id, pipeline и кодом без
контроллерского CLI. Его finish, отказ и прежние рассуждения не входят в задание.
Определяет работу только собственный start. Реализатор возвращает JSON с `code`,
необязательными `notes` и `blocked_reason`. Замечания объясняют технические детали
и ограничения; они не содержат выдуманные измерения. Если план невыполним,
реализатор сообщает причину вместо замены модели / гипотезы. Пустой код с
blocked_reason не завершает ноду сразу: контроллер возвращает last_refusal с
source=model_claim, verified=false для пересмотра на основе контракта и профиля.
Это расходует тот же лимит 20 запросов / общий дедлайн. Последние previous_code,
execution_error и failed_stage при отказе сохраняются; утверждение модели не
подменяет наблюдаемую ошибку. При наличии кода контроллер проверяет его, даже если
ответ также содержит blocked_reason. Неуказанные детали
реализации можно выбрать и объяснить в notes. Полное смысловое соответствие
произвольного Python плану автоматически пока не доказывается.

Скрипт определяет `fit_predict(fit, validation, test, preparation)`, возвращающий
два DataFrame предсказаний в порядке validation / test. Fit содержит target;
из переданной модели validation target удалён. Реализатор не пишет scorer.
Исполнитель обучается только на fit; отдельного refit по всем размеченным train
после оценки сейчас нет. Baker получает это ограничение и просьбу использовать
не более двух параллельных training jobs при двух одновременных экспериментах.
Контроллер добавляет общий CLI-вход: `python experiment.py --start start.json`.

После сохранения start выполняются генерация кода и короткая проверка на части
данных. Ошибка проверки или полного запуска возвращается реализатору вместе с
текущим кодом и этапом отказа. До 20 фактических API-запросов на ноду, включая
JSON-repair; успех завершает цикл сразу. Общий лимит времени имеет приоритет.
Одинаковый скрипт после ошибки пока не перехватывается: если реализатор снова
возвращает тот же код после таймаута, контроллер повторно исполняет его. Это
подтверждено одинаковым SHA-256 в тесте на 20 нод. Отдельного общего дедлайна ноды
нет: выбранный лимит исполнения ограничивает один процесс, а не все исправления вместе. Такая
нода может занять остаток глобального бюджета даже после завершения остальных.
Ответ содержит полный скрипт; следующая итерация получает только последнюю версию
и диагностику, без накопления переписки и общей истории delta. Временный
результат smoke-test удаляется. Пример start (имена и алгоритм иллюстративные):

```json
{
  "schema_version": 3, "node_id": "node_000", "parent_id": null, "source": "qwen",
  "preparation": "../../preparation.json", "preparation_sha256": "<реальный хеш>",
  "context": {
    "task": "/path/to/dataset/condition.md", "task_sha256": "<реальный хеш условия>",
    "purpose": "baseline", "delta_nodes": 0,
    "extraction": "../../extraction.json", "extraction_sha256": "<реальный хеш extraction>",
    "preparation_code": "../../prepare.py", "installed_libraries": {"scikit-learn": "1.5.2"}
  },
  "hypothesis": {
    "rationale": "Константный baseline", "expected_effect": "Проверить полный цикл",
    "pipeline": {"data": {}, "preprocessing": {},
                 "model": {"name": "constant", "strategy": "mean"}, "training": {}}
  },
  "implementation": "experiment.py",
  "outputs": {"validation": "validation_predictions.csv", "submission": "answer.tsv"},
  "timeout_seconds": 240.0
}
```

Хеши в примерах — обозначения; в настоящих файлах записывается SHA-256.
Контроллер фиксирует хеш кода после записи, проверяет его при полном запуске;
worker также проверяет хеши start, preparation, данных, prepare.py и split.
Каждая версия исходника фиксируется хешем перед полным запуском. Техническое
исправление остаётся в той же ноде; изменение модели / плана требует нового start.
После успеха или исчерпания попыток контроллер сохраняет окончательный finish.
Последний исходник сохраняется и при отказе проверки, его хеш есть в finish;
AST-проверка остаётся обязательной до исполнения. Последняя техническая ошибка
записана в execution.log, даже если subprocess ещё не запускался. Для вычисляемого
значения на верхнем уровне диагностика предлагает перенести его внутрь функции.

Start / finish версии 3; delta / nodedelta — 1; extraction / preparation / report — 2.
Ранее сохранённые JSON не переписываются: viewer читает обе формы. Исполнение
старых experiment.py с новым runtime не поддерживается; нужен новый запуск.
Возврат к прежнему runtime — checkout предыдущего коммита, без преобразования данных.

## Выполнение и результат

Модель получает fit, validation без target и test. Обучается на fit; тестовые
предсказания первого baseline также делаются этой моделью, без отдельного refit
на всём train. Общая обвязка сохраняет validation predictions, вызывает общий
scorer на настоящих target и сохраняет submission в формате из условия.

`finish.json`: completed / failed / timeout, stage (implementation / check /
execution), длительность работы исполнителя (генерация, проверки и запуски, без очереди), metric, value,
evaluation_status, пути результатов, start_sha256, preparation_sha256, code_sha256,
notes реализатора и ошибка. Отказ после записи start также сохраняет finish,
включая невалидный ответ модели, отказ реализовать план, ошибку проверки и таймаут.
Если исходник не создан, code_sha256 — null. Отсутствующая / упавшая метрика
не подменяется нулём: предсказания могут быть готовы, а оценка unavailable / failed.
Число score может быть отрицательным, если так определена кастомная метрика.

Процессы запускаются с таймаутом и очищенным окружением без API-ключа. Код имеет
ограниченный интерфейс / импорты; это не полноценная OS-песочница. Установка
библиотек и сетевые обращения в генерируемом коде не предусмотрены.

Лучший файл ответа публикуется рядом с Markdown. Для ранжирования нужны score и
известное направление: тогда `best.json` указывает на лучшую ноду. Без оценки
сохраняется первый пригодный ответ, но он не объявляется лучшим. Ошибка или
ухудшение кандидата не перезаписывает результат лидера.

## Delta и развитие дерева

После каждого finish контроллер вызывает `summarize()` в runner.py. Дополнительного
LLM-вызова нет: числа и структурные изменения вычисляет Python. Сохраняются:

- `nodes/node_*/delta.json`: node_id, parent_id, исходная hypothesis, полный result
  из finish, comparisons и best_node_id на момент этой ноды.
- Общий `delta.json`: хеш общей preparation, metric, список этих записей nodes и
  актуальный best_node_id. В нём достаточно контекста для следующего Baker.

Каждое comparison содержит reference_id, changes (path / before / after),
comparable / reason, value_delta и improvement. Сравниваются четыре блока pipeline,
включая произвольные имена алгоритмов / параметров. Списки сравниваются целиком;
текст rationale не считается изменением архитектуры.

`value_delta = new_score - reference_score`. Для minimize положительное improvement
равно `reference_score - new_score`, для maximize — `new_score - reference_score`.
При отсутствии score, неизвестном направлении или разных preparation / metric
численная дельта остаётся null с причиной; структурные изменения всё равно видны.
Отрицательные кастомные score допустимы. Различия не доказывают причинность.

После одиночного baseline Baker предлагает пару: improve улучшает лидера,
explore проверяет другой алгоритм / существенно другой pipeline или возвращается
к прежней проигравшей ветке. Первую пару просят сделать двумя разными подходами.
Имена моделей свободные; семантику разнообразия выбирает Qwen. При равном score
сохраняется более ранний лидер; без score improve продолжает последнюю успешную
ноду. До первого успешного baseline поиск не запускается.

Baker получает исходное условие, preparation, библиотеки, pipeline / код / score
лидера, компактные history / pending, доступных родителей и остаток бюджета.
Extraction, прежние rationale / expected_effect, полные finish и comparisons в
следующие запросы не дублируются. Запись истории содержит node_id, parent_id,
status, score, время всей ноды (включая генерацию / исправления), этап, последнюю
строку ошибки, источник артефакта и pipeline_changes. error_source различает
runtime, controller и model_claim: отказ модели не становится доказанным свойством
данных / алгоритма, а один неудачный запуск не запрещает семейство моделей.
Эта краткая память собирается из delta без отдельного файла или LLM-вызова.
Baker также получает runtime_contract, профиль missing / distinct и просьбу
обосновывать изменения измерениями с учётом времени. Диагностика ошибок по классам,
residuals и разрыв train / validation автоматически пока не вычисляются.
Изменения заменяют целые
блоки parent.pipeline; отсутствующий блок наследуется без изменений. Так сохраняются
произвольные параметры, форматы и изменения данных без повторения общих блоков.
Полные артефакты остаются на диске. Ответ содержит hypotheses: каждый элемент —
purpose, parent_id, hypothesis. Контроллер проверяет каждое предложение отдельно:
структуру, родителя, parent improve = выбранный лидер и отсутствие одинаковых pipeline.
Отклоняются также точные повторы pipeline из истории и pending-планов снимка.
Это равенство JSON, без распознавания смысловых повторов с иными описаниями.
При repair перечисляются все повторившиеся предложения пары с их ролью и ID
совпавшей ноды; Baker должен изменить pipeline, а не только пояснение гипотезы.
Корректная гипотеза сразу сохраняется и запускается, даже если вторая отклонена.
Следующий запрос содержит только отклонённые requested_purposes, последний неверный
pipeline и конкретную ошибку с ID совпавшей ноды. Ошибка выделяется в начале и конце
контекста. После двух последовательных отклонений одинакового pipeline задаётся
new_direction: другое изменение лидера для improve, другой подход для explore;
предыдущая переписка очищается. Последняя причина отказа остаётся в контексте.
Имена алгоритмов и набор изменений не зашиты в код. На baseline / одну порцию — до 10
API-запросов суммарно, включая первый запрос, JSON-repair и сетевые повторы.
Перед каждой попыткой контроллер пересобирает delta, pending, лидера, доступных
родителей и остаток времени; JSON проверяется относительно этого же снимка.
Порция сохраняет общий счётчик запросов при переходе к исправлению одной роли.
При остатке в одну ноду
запрашивается только improve. Explore выбирает родителя из available_parents:
успешные ноды, а если их нет — последняя попытка. Родители пары могут различаться.

Контроллер сохраняет каждый принятый start до его исполнения. context.purpose хранит роль;
context.delta_nodes — число завершённых попыток в снимке истории для этого запроса.
Это не номер ноды и не глубина дерева. Пока Baker планирует, другие finish уже
могут обновить лидера; сохранённые планы / родители соответствуют снимку принятого
запроса. После отклонения новая попытка уже использует обновлённый снимок. При
раздельном принятии роли и context.delta_nodes у соседних ID могут различаться;
номер ноды больше не задаёт её роль.

Очередь обслуживают два независимых исполнителя. После любого finish контроллер
сразу обновляет delta / best. Освободившееся место берёт ожидающий start; если очередь
пуста и лимит позволяет, запускается один Baker для новой пары. Другой исполнитель
продолжает работу; результаты принимаются и во время ожидания Baker. Обычно вне
исполнителей остаётся не более одного ожидающего start. Новые ID назначаются по
числу всех принятых start, включая очередь и работающие ноды. Все принятые гипотезы
исполняются в пределах времени; общие scorer / split / подготовка не меняются.

Для `solution.py` профиль платформы — 100 нод, 10 500 с общего времени и до 1200 с
на один процесс. Явные параметры имеют приоритет. Отдельная отладочная CLI-команда
сохраняет 10 нод / 600 с / 240 с. `--max-nodes 1` оставляет только baseline;
smoke занимает до 45 с. Исправления кода ограничены числом
API-запросов и общим дедлайном; отдельный API-запрос ждёт до 300 с по умолчанию
или меньше, если общий бюджет заканчивается. Параметр — `QWEN_TIMEOUT_SECONDS`.
Общий предел API-попыток: `12 + 30 * max_nodes`, включая repair. Это общий
ограничитель для всех ролей; локальный максимум реализатора — 20 запросов на ноду.
Лимит реализатора проверяется перед каждым HTTP-запросом, а не по числу версий кода.
Счётчик локален для ноды, общий бюджет разделён всеми ролями. API-записи содержат
node_id. Report сохраняет running_nodes, queued_nodes, planning. Окружение и
threadpoolctl задают по два потока BLAS / OpenMP; параллелизм joblib определяется
сгенерированной моделью. Жёстких OS-лимитов CPU / RAM процесса нет.
Сетевая ошибка, таймаут API или HTTP 5xx допускают повторы с паузами 2 с, затем по 4 с,
в пределах 10 API-попыток Baker или трёх на ответ остальных ролей. У остальных ролей
по-прежнему один JSON-repair на ответ. Provider JSON-mode не используется;
отправляется `reasoning_effort=none`, максимум ответа — 32 768 токенов.
Разбирается только content, при необходимости без целой внешней Markdown-обёртки;
проверки схемы и цитат сохраняются. Все запросы учитываются; причина соединения выводится как имя класса,
без тела ответа, заголовков и ключа.
Ошибка конкретной
ноды записывается в finish / delta и поиск продолжается. После исчерпания попыток
Baker или API-ошибки уже принятые планы продолжают работу. Новая порция возможна,
когда delta содержит новый finish относительно начала неудачной порции. Так принятая
ветка продолжает развиваться после отказа другой роли. Повторное планирование на
неизменившейся истории после исчерпания 10 запросов блокируется; без работающих нод
и новых результатов поиск завершается. Восстановимые отказы Baker записываются в
warnings; окончательная остановка без прогресса — также в errors. Общий дедлайн
отменяет API-запросы и процессы; принятые незавершённые ноды получают timeout / finish.
Лидер сохраняется. Автоматического resume пока нет.
Контроль классификации показал повторение планов на старом снимке и новую пару
на свежем. Теперь контекст обновляется при повторе; это не гарантирует, что Qwen
исправит ответ за 10 запросов. Исчерпание лимита всё ещё может завершить поиск до
достижения лимита нод. Подробности и диагностические артефакты — README.
В тесте `classification-async15-retry10` первый повтор исправлен на свежем снимке,
но следующая порция отклонена все 10 раз из-за повторного explore KNN. Поиск
завершился после 9 успешных нод; ошибки исполнителей и сети причиной не были.
Раздельное принятие добавлено после этого прогона и проверяется HTTP-имитацией с
реальными subprocess. Следующий live-тест `classification-async15-partial` дошёл до
15 нод без повторов Baker: 11 успешных, 4 отказа. Он выявил прежний дефект
продолжения после failed baseline и ошибочные blocked_reason; барьер и пересмотр
отказов добавлены после этого прогона. Все численные
результаты и submission проверены независимо; подробности — README.

Run report: ready — достигнут лимит нод и есть оценённый лидер; partial — есть
предсказания, но нет оценки или поиск остановлен раньше; failed — пригодного ответа
нет. stop_reason и completed_nodes / failed_nodes дополняют статус. Сбой подготовки
останавливает запуск до нод; отказ baseline — до развития дерева. Если baseline
записал предсказания, но scorer упал, файлы сохраняются, report=partial / baseline_failed.
Глобальная delta обновляется атомарно после каждой ноды.

## Просмотр и проверки

`python3 viewer.py` читает artifacts, показывает четыре блока / evidence,
подготовку, общую delta и дерево экспериментов. Доступны JSON и исходники. Обновление каждые 2 с;
экспорт HTML — снимок. Viewer не вызывает API, не читает CSV / .env и не исполняет
код. Он показывает записанные checkpoint’ы, не определяет, жив ли процесс.

Тесты используют имитированный Qwen HTTP и настоящие subprocess / данные:
новые имена, PSV + JSON Lines, кастомная формула и TSV из трёх колонок, leading-zero
ID, честная оценка на сохранённых строках, start до реализации / неизменность при
исправлении, отказы разных этапов, незавершённая
метрика, таймаут и отсутствие API-ключа в worker. Реальные live-проверки описываются
отдельно по их сохранённым report / finish; успешный mock не выдаётся за ответ Qwen.
