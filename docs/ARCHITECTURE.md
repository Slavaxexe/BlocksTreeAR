# Архитектура ML-агента

Цель — получить простой работающий baseline, затем улучшать его отдельными
экспериментами. Код компактный: существующие модули оркестрируют этапы; на одну
новую гипотезу создаётся один скрипт реализации. Артефакты запуска хранятся вместе.

## Состояние реализации

Уже работают четыре асинхронных Qwen-extractor’а с evidence, сохранение ответов,
локальная проверка и HTML-просмотрщик. **Текущий extractor ещё ограничен двумя
типами задач, RMSE / Macro F1 и CSV.** Отделение универсального извлечения от
поддержки исполнителем, новая раскладка ниже и `preparation.json` пока являются
проектом следующего изменения. Показанные JSON — примеры будущих контрактов.

Старый полный цикл сохранён как черновик: worker собирает заранее написанные
sklearn pipeline, произвольный Python для гипотез Qwen сейчас не генерирует.

## Этапы

```text
Markdown → четыре extractor’а → extraction.json
  → чтение / осмотр данных → preparation.json
  → план baseline → код → start.json → выполнение → finish.json
  → сравнение результатов → следующая гипотеза → код → start → finish …
```

Извлечение, подготовка и генерация гипотез — отдельные роли. Для этого не нужны
постоянно живущие процессы или отдельный исходный модуль на каждую роль.

## Извлечение условия

Четыре запроса получают один исходный Markdown, каждый со своим вопросом:

- `problem`: задача, target, единицы, классы, оговорки и ограничения из условия.
- `data`: перечисленные файлы, их роли и форматы, ID, параметры чтения.
- `metric`: основная и дополнительные метрики, направление, определение,
  формула или ссылка на предоставленный код, если они указаны.
- `output`: требуемые файлы ответа, структура, тип предсказаний и порядок строк.

Названия метрик, файлов и форматов свободные. Схема фиксирует структуру JSON.
Кастомную метрику сохраняем как описание с evidence, даже если пока не умеем её
считать. Неуказанное значение — `null` или пустой список; неоднозначность остаётся
явным замечанием. Преобразования признаков и выбор модели здесь не придумываются.

`evidence[field]` содержит точные цитаты из Markdown. Проверяем JSON / типы,
наличие подтверждений и существование цитат в исходнике с нормализацией пробелов.
Это подтверждает происхождение фразы, но не гарантирует верное понимание смысла.
Проверка доступности файлов, метрик и загрузчиков относится к подготовке.
Неизвестный формат или метрика сами по себе не означают ошибку извлечения.

Принятые ответы сохраняются по мере готовности. После успешного извлечения
обычный Python объединяет четыре блока в `extraction.json`; отдельный LLM-вызов
не нужен. Технический `report.json` хранит статус, ошибки, замечания, попытки API,
usage и контрольную сумму исходного Markdown. При невалидном ответе допустим
один repair. Сырые ответы API и внутренние рассуждения сейчас не сохраняются.

## Подготовка

`preparation.json` описывает реальные входы и общие условия экспериментов:
пути и форматы файлов, измеренный профиль, найденные target / ID, validation
и доступность вычисления метрики. Факты получают чтением файлов, а не из догадки
LLM. Если нужен новый загрузчик или разъяснение условия, это отмечается в `issues`.

Пример для публичной регрессии; размеры и число пропусков взяты из сохранённого
профиля, структура файла предлагается для следующего этапа:

```json
{
  "schema_version": 1,
  "status": "ready",
  "extraction": "extraction.json",
  "data": {
    "train": {"path": "../../data/raw/regression/train.csv", "format": "csv", "rows": 53308},
    "test": {"path": "../../data/raw/regression/test.csv", "format": "csv", "rows": 22449},
    "sample_submission": "../../data/raw/regression/sample_submission.csv",
    "target_columns": ["site_eui"], "id_columns": ["id"]
  },
  "profile": {"missing_train_cells": 136533},
  "validation": {"strategy": "holdout", "fraction": 0.2, "seed": 42, "split_file": "split.npz"},
  "metric": {"name": "RMSE", "direction": "minimize", "implementation": "builtin:rmse", "status": "ready"},
  "issues": []
}
```

Профиль по необходимости содержит колонки с типами, пропуски и распределение
target; строки датасета в JSON не копируем. `evidence` относится к извлечению
из Markdown: профиль подтверждается ссылками на реальные файлы. Пути в общих
артефактах считаются относительно каталога запуска.

`status` — `ready`, `partial` или `blocked`; причины — в `issues`. Для кастомной
метрики без реализации `metric.status = "needs_implementation"`,
`implementation = null`. Если данные и формат ответа понятны, можно получить
предсказания без score. Такие результаты не участвуют в выборе лучшей модели.

Validation выбирается по условию и устройству данных; holdout 80/20 выше — пример,
а не универсальное правило. Индексы split сохраняются один раз для всех нод.
Готовая метрика использует общий вычислитель. Для кастомной роль реализатора
при подготовке может однократно создать общий `metric.py` по определению из
условия; если определения не хватает, реализация остаётся неготовой.
Метрику, данные и split фиксируем до сравнения нод;
их изменение означает новый запуск. Необходимые сведения сверяем и с общими
[ограничениями кейса](TASK_BRIEF.md), которые не выдаём за содержимое task.md.

## Гипотеза, код и start.json

Сначала baker получает extraction / preparation и предлагает описание
эксперимента: данные, preprocessing, модель и обучение. Для нулевой ноды это
простейший рабочий baseline. Это план, а не измеренный результат.

Роль реализатора получает план и общие условия, создаёт один `experiment.py`
в каталоге ноды. Вначале можно выполнять обе роли последовательными запросами
к той же модели. Каталог ноды выделяет контроллер; ID и родителя назначает код.

После подготовки кода и короткой проверки запуска контроллер сохраняет
окончательный `start.json` с планом, ссылкой на preparation и хешем исходника:

```json
{
  "schema_version": 1,
  "node_id": "node_000", "parent_id": null,
  "preparation": "../../preparation.json",
  "hypothesis": "Проверить полный цикл на предсказании среднего target",
  "pipeline": {
    "data": {"features": "from_preparation"},
    "preprocessing": [],
    "model": {"name": "constant", "params": {"strategy": "mean"}},
    "training": {}
  },
  "implementation": {"file": "experiment.py", "sha256": "<хеш фактического исходника>"},
  "outputs": {"validation": "validation_predictions.csv", "submission": "submission.csv"},
  "limits": {"timeout_seconds": 120}
}
```

Ссылка на preparation выше считается от каталога ноды. Хеш в примере —
обозначение места для реального SHA-256, а не готовое значение. После начала
эксперимента start и исходник не переписываются; исправление оформляется новой
нодой. Зависимости берём из общего окружения проекта, без requirements на ноду.

Единый предполагаемый вход: `python experiment.py --start start.json` из каталога
ноды. Скрипт получает входы и параметры через start / preparation, обучает модель
и записывает предсказания по путям `outputs`; в примере выбран CSV.
Общая обвязка вычисляет score по сохранённому
split и одной реализации метрики. Гипотеза не выбирает себе новый способ оценки.
Запуск — отдельный процесс с таймаутом, без API-ключа в окружении.

`finish.json` записывает фактический статус, длительность, score либо причину
его отсутствия, пути результатов и ошибку при отказе. Успешная генерация Python
ещё не означает успешный эксперимент. При недоступной метрике score остаётся
`null`; подменять её другой метрикой или придумывать число нельзя.

## Сравнение и хранение

Summarizer обычным кодом сравнивает устройство и реальные результаты нод.
Baker получает компактную сводку и предлагает следующую гипотезу. `best.json`
указывает на лучшую сопоставимую ноду. Baseline, родителя и текущего лидера
достаточно для первых сравнений; полная матрица всех пар пока не нужна.

Предлагаемая раскладка:

```text
artifacts/<run-id>/
├── extraction/             problem.json, data.json, metric.json, output.json
├── extraction.json         Четыре блока с evidence
├── report.json             Журнал этапов и запросов
├── preparation.json        Файлы, профиль, validation, поддержка исполнителем
├── split.npz               Общие индексы для табличного holdout, если он выбран
├── metric.py               Только если нужен собственный вычислитель метрики
├── nodes/node_000/
│   ├── start.json           План и ссылка на конкретный исходник
│   ├── experiment.py        Одна реализация эксперимента
│   ├── finish.json          Реальный результат
│   ├── validation_predictions.*
│   └── submission.*        Формат определяется условием
└── best.json                Указатель на победителя, без копии всех артефактов
```

Данные, split и метрика общие для запуска; в каждой ноде их не дублируем.
Полезные финальные результаты сохраняем. Одноразовые синтетические прогоны,
повторы и промежуточные скриншоты удаляем после проверки. Ошибка рабочего
эксперимента остаётся его результатом, автоматического удаления таких нод нет.

## Текущие артефакты и запуск

До внедрения новой раскладки финальные ответы реального Qwen находятся в
`artifacts/extraction/regression-stage1-final/` и
`artifacts/extraction/classification-stage1/`: оба `ready`, четыре принятых блока.
Регрессия — 4 вызова, 11 379 токенов; классификация — 5 вызовов, 8 884 токена,
один repair для output. Проверены 20.10.2026; в API передавался текст условия,
CSV читались локально. Эта проверка относится к прежнему ограниченному контракту.
Сохранены по одному полному старому ML-прогону в `outputs/regression/` и
`outputs/classification/`; это не запуски новой архитектуры.

```bash
uv run --locked python -m alfa_agent extract --task data/raw/regression/task.local.md --key-stdin
python3 viewer.py
```

Просмотрщик читает записанные JSON, обновляется каждые две секунды и не запускает
LLM / обучение. Сейчас он показывает старую раскладку; при миграции обновляется
вместе с писателем артефактов. Ключ вводится скрыто или берётся из окружения,
в артефакты / git не записывается. Дерево исходников и назначение скриптов —
в [карте проекта](../PROJECT_MAP.md).
