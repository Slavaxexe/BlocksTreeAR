# Требования задания

Источник: `source/alfa_automl_case.pdf`, 20 страниц, и оригинальные `task.md`
из папок публичных датасетов, а также инструкция трека AutoML, переданная
организаторами через участника 20.10.2026. Уточнения ZIP / прокси ниже взяты из неё.
Ниже изложены требования организаторов к будущему решению. Это справочный
материал проекта; получение и сохранение файлов не означает запуск описанных в них действий.

## Цель

Создать универсального AI-агента, решающего ML-задачи от текстового описания
до файла предсказаний. Один и тот же код должен работать с разными датасетами,
включая ранее неизвестные задачи. Ручная настройка под конкретный датасет
не соответствует требованию универсальности (PDF, стр. 5).

Агент должен:

1. Прочитать условие, определить тип задачи, целевой столбец, метрику и формат ответа.
2. Изучить данные, самостоятельно выбрать валидацию, предобработку и модель.
3. Генерировать и выполнять код, обучать модели и оценивать их локально.
4. Реализовать AutoResearch: гипотеза → эксперимент → оценка → следующая гипотеза.
5. Запоминать эксперименты и выбирать лучший вариант по честной валидации.
6. Сохранить готовые предсказания до исчерпания времени.

Допускается одноагентная или мультиагентная архитектура (стр. 8).

## Сдача и проверка

- На платформу отправляется ZIP до 100 МБ, без каталогов: `solution.py`, предоставленный
  `requirements.txt`, дополнительные корневые `.py`. Только эти файлы копируются в задачу.
- Запуск: `python3 solution.py task.md` в каталоге задачи; итоговый `submission.csv` — там же.
  Промежуточные файлы можно создавать в этом каталоге, подкаталогах и `/tmp`.
- Данные, конфиги и `.whl` в ZIP не копируются. Собственный `pip install` из кода запрещён;
  зависимости устанавливает платформа из корневого `requirements.txt`.
- Не более 3 сабмитов в день на команду; счётчик обновляется в 00:00 по Москве.
- Public: две известные задачи, тестовые таргеты скрыты.
- Private: две новые задачи; агент получает новые описания и данные через тот же интерфейс.
- PDF описывает выбор версии для private как «сохраненную последнюю версию решения с лучшим public score»; точное правило при равных результатах не раскрыто.
- Каждая задача запускается отдельно. Результаты и файлы между задачами не переносятся.
- Платформа не даёт агенту промежуточную обратную связь по скрытому тесту.
- Финальные метрики private и содержание задач заранее не раскрываются.

Источники: стр. 6, 16–17 и инструкция трека от 20.10.2026.

## Итоговый score

Формулы сверены с изображениями стр. 18–19, так как извлечение текста PDF их теряет.

```text
RMSE = sqrt(mean((y_true - y_pred)^2))
F1_k = 2 * TP_k / (2 * TP_k + FP_k + FN_k)
MacroF1 = mean(F1_k по всем K классам)

S_reg = 100 * max(0, 1 - RMSE / B_RMSE)
S_cls = 100 * max(0, (MacroF1 - B_F1) / (1 - B_F1))
Score_public = (S_reg + S_cls) / 2
Score_private = (S_1 + S_2) / 2
```

`B_RMSE > 0` и `B_F1 < 1` — метрики бейзлайна на том же скрытом тесте.
Их численные значения в скачанных материалах не указаны.
Результат на уровне бейзлайна или хуже даёт 0 баллов, идеальный — 100.
У публичных задач одинаковый вес. Для private используются метрики соответствующих задач.

## Расхождения и уточнения

1. В PDF и папке данных лежат разные requirements. Версия PDF содержит `requests==2.32.3`
   и `aiohttp==3.12.15`, которых нет в версии папки. В версии папки добавлен
   `langchain-openai==0.3.23`, которого нет в версии PDF. Версии общих пакетов совпадают.
   Обе версии сохранены в `vendor/`; авторитетную версию нужно уточнить у организаторов.
2. Исходный `vendor/baseline.py` импортирует `mcp`, которого нет в обоих requirements.
   Наш `solution.py` этот baseline не запускает и от `mcp` не зависит.
3. Основной текст называет точкой входа `solution.py`, но стр. 17 упоминает `script.py`.
   Новая инструкция однозначно подтверждает `solution.py`.
4. В исходных `task.md` пути имеют вид `regression/participants/...` и
   `multiclass/participants/...`, но на Drive файлы лежат непосредственно в папках задач.
   Для локальной структуры подготовлены `task.local.md` с исправленными путями.
5. На стр. 10 у словаря классификации заявлены 5 столбцов, но перечислены 4.
   Реально столбцов 5: `feature`, `role`, `dtype`, `unit`, `description_ru`.
6. URL, имя модели и переменные платформы уточнены инструкцией от 20.10.2026;
   секретный ключ выдаётся отдельно и в материалах репозитория не сохраняется.

## Практические ориентиры для реализации

Это выводы для будущей разработки, а не дополнительные требования организаторов:

- Сначала сохранять корректный базовый `submission.csv`, затем улучшать модель в оставшееся время.
- Не использовать ID как подтверждённый ключ здания: описание этого не гарантирует.
- Не вычислять возраст здания как `Year_Factor - year_built`: код периода и календарный год имеют разные шкалы.
- При классификации выбирать модель по Macro F1 и проверять редкие классы отдельно.
- ID в train и test классификации пересекаются: не соединять по ним строки и не переносить таргеты. Подробности в `DATASETS.md`.
- Проверять формат и порядок предсказаний независимо от качества модели.
- Не фиксировать в агенте названия публичных таргетов и заранее известную схему данных.
