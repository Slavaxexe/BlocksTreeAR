## Исправления

**Сериализация сгенерированных модулей.** Регистрация в sys.modules сохранена — она нужна dataclass и аннотациям. После успешной загрузки модуль регистрируется для сериализации по значению в cloudpickle и встроенном в joblib cloudpickle. Теперь loky получает реализацию функций/классов, а не ссылку на имя generated_…, отсутствующее в новом интерпретаторе. Хеш исходника и восстановление предыдущего модуля при ошибке загрузки проверяются по-прежнему. Сторонние пакеты не добавлены: оба сериализатора уже в официальных зависимостях.

**API URL.** Как Blocks, валидатор допускает query, userinfo и fragment. Сохраняется только проверка абсолютного HTTP(S), хоста и корректного порта. При этом недостаточно просто снять запрет: установленный SDK склеивает `http://proxy/v1?team=example` в путь `/v1` с query `team=example/chat/completions`. Адаптер теперь отделяет query от base URL и передаёт параметры через публичные настройки HTTPX. Фактический запрос идёт на `/v1/chat/completions?team=example`. Повторяющиеся ключи, пустые значения и закодированные символы проверены отдельно. Обычные URL без query используют прежний путь. Адрес, ключ и модель по-прежнему берутся из окружения, запасных хостов нет. Если URL содержит userinfo, действует стандартное поведение SDK/HTTPX: HTTP Basic из URL; оно не заменяется самодельной логикой.

В предыдущем ZIP изменены только alfa_agents.py, alfa_config.py, alfa_data.py, alfa_qwen.py. Остальные 11 файлов, включая solution.py, runner, worker, toolkit, requirements и выключенный fallback, идентичны. Все ранее согласованные пять исправлений сохранены.

Нюансы:

- Отсутствие нашего отдельного semaphore не создаёт неограниченное число корутин: поиск запускает до 6 экспериментальных узлов и один планировщик; первичный разбор — 4 роли. При нынешнем устройстве поиска одновременно обычно не более 7 LLM-запросов. Лимит 8, как у Blocks, был бы отдельной защитой для будущих изменений, но его сейчас не включали.
- Blocks выделяет 1 поток через BLAS/OpenMP, threadpool_limits и принудительное n_jobs/thread_count в фабрике поддерживаемых моделей. Наш toolkit использует 2; произвольный сгенерированный код получает эту инструкцию, но AST-валидатор не запрещает написать n_jobs=-1. Это известное ограничение управления ресурсами, а не воспроизведённая причина исторического падения.
- При 8 CPU шесть экспериментов по два потока могут запрашивать 12 потоков одновременно. Для поведения ближе к Blocks разумный следующий выбор — 6 × 1; это уменьшает конкуренцию CPU, но может замедлить отдельную модель. Настройка не изменена без отдельного решения пользователя.
- У Blocks research_timeout=120 указан в точке входа, но research_unlimited=True отменяет этот отдельный лимит для исследовательского узла: применяются дедлайн фазы и общий дедлайн. Начальная фаза всё равно ограничена eda_seconds=720. Затем исследователи могут работать рядом с поиском.
- При временном HTTP 429 Blocks делает до 5 неуспешных сетевых попыток и вводит общую паузу для ролей; у нас до 3 на обращение и локальные паузы. При quota/budget Blocks останавливает новые вызовы сразу; у нас сохранены согласованные 3 попытки, затем общая остановка.

Источники значений в Blocks: solution.py:14–24; runner.py:32–48, 52–68, 350–352, 490–513, 523–538; agents.py:114–124, 201–229, 324–350; worker.py:181–186; operations.py:168–174. Машиночитаемая сводка — `artifacts/final-20261025/launch_comparison.json`.
