# Автономный цикл ML-экспериментов: AIDE, RD-Agent и autoresearch

## Какую архитектуру стоит заимствовать?

### Takeaway
Для трёхчасового прототипа подходит собственный небольшой контроллер: проверенная гипотеза → изолированный запуск → измеренная метрика → краткая сводка → следующая гипотеза. AIDE обосновывает дерево решений и ограниченный контекст; RD-Agent — разделение исследовательской и инженерной ролей; autoresearch — неизменяемую оценку и ограниченный эксперимент. Это рекомендации по адаптации, а не обещание повторить результаты авторов. [AIDE, §3](https://arxiv.org/html/2502.13138v1); [RD-Agent, §2](https://arxiv.org/html/2505.14738v1); [autoresearch/program.md](https://github.com/karpathy/autoresearch/blob/master/program.md)

### Cited Findings
- **AIDE:** узел — самостоятельный Python-скрипт с оценкой; ребро — попытка улучшить родителя. Политика выбирает draft/debug/improve, ограничивает отладку и обычно улучшает лучший корректный узел. Summarizer передаёт идеи, метрики и существенные ошибки вместо полного журнала. Улучшение предлагается как одно атомарное изменение. [AIDE, §3.1–3.2](https://arxiv.org/html/2502.13138v1)
- **RD-Agent:** Researcher использует performance feedback для гипотез; Developer использует execution errors для исправления реализации. Применяется сначала отладка на выборке, затем полноценный запуск. Несколько трасс могут обмениваться результатами и сливаться. [RD-Agent, §2.1–2.2](https://arxiv.org/html/2505.14738v1)
- **autoresearch:** первая попытка фиксирует baseline; менять разрешено training-код, оценочный harness и зависимости фиксированы. Есть журнал keep/discard/crash, пятиминутное обучение и прекращение чрезмерно долгого запуска. Это single-GPU LLM-training пример, а не готовый табличный CPU AutoML. [program.md](https://github.com/karpathy/autoresearch/blob/master/program.md)

### Inferences
- **Минимальная реализация:** один scheduler, один summarizer, один hypothesis baker и 1–2 worker-процесса. LLM-роли можно реализовать разными промптами к одной Qwen-compatible модели; полноценный multi-agent framework для этого не требуется. Основа адаптации: [AIDE](https://arxiv.org/html/2502.13138v1), [RD-Agent](https://arxiv.org/html/2505.14738v1).
- **Стартовый узел, проектный контракт:** `schema_version`, `experiment_id`, `parent_id`, `hypothesis`, `single_change`, `dataset_hash`, `split_id`, `metric`, `direction`, `seed`, `model_config`, `code_hash`, `timeout_s`, `cpu_threads`. Сначала достаточно `json` стандартной библиотеки с явными проверками типов, enum, обязательных полей и допустимых путей; это не требует новой ML-зависимости.
- **Финишный узел, проектный контракт:** те же идентификаторы плюс `status` (`success/error/timeout/invalid`), `elapsed_s`, `exit_code`, `validation_score`, `predictions_path`, `prediction_schema`, `error_summary`. Поля метрики и статуса заполняет контроллер после проверки результата; текст LLM не является доказательством успешного обучения. `NaN`, бесконечность и отсутствующий prediction-файл означают invalid, а не плохую числовую оценку. Принцип внешней оценки заимствован из [autoresearch](https://github.com/karpathy/autoresearch/blob/master/program.md).
- **Summarizer:** числовое ранжирование и дельты считает Python; LLM объясняет различия и предлагает причины как гипотезы. На каждую новую попытку сравнивать её с родителем, baseline и incumbent. Полные попарные сравнения требуют `n(n−1)/2` пар: 100 запусков → 4950 пар. Эта арифметика сама по себе не даёт пользы для выбора следующего эксперимента. Передавать baker только top-3, последние 5 результатов, несколько провалов, уже проверенные изменения и остаток бюджета. Это наш ограниченный вариант summary-подхода [AIDE](https://arxiv.org/html/2502.13138v1).

### Gaps
- Источники не подтверждают, что конкретная Qwen-модель надёжно пишет ML-код или соблюдает JSON-контракт в заданном окружении. Нужна короткая локальная проверка; результаты AIDE/RD-Agent на других моделях этого не гарантируют.
- Схемы JSON выше — предлагаемый контракт проекта, не стандарт AIDE/RD-Agent.

## Как обеспечить рабочий baseline и постоянный экспорт лучших предсказаний?

### Takeaway
Сначала полностью выполнить простой baseline, включая проверенный файл предсказаний; только потом включать автономный поиск. После этого артефакт лучшей завершённой попытки сохраняется независимо от падений следующих экспериментов. Это предлагаемое условие надёжности прототипа, опирающееся на baseline-first подход [autoresearch](https://github.com/karpathy/autoresearch/blob/master/program.md).

### Cited Findings
- `DummyClassifier` игнорирует признаки и служит baseline; стратегия `prior` возвращает частоты классов через `predict_proba`, а не случайные вероятности. Детерминированные стратегии позволяют проверить контракт вывода без поиска модели. [Официальная документация](https://scikit-learn.org/stable/modules/generated/sklearn.dummy.DummyClassifier.html)
- В протоколе AIDE конечная отложенная выборка отличается от внутренней validation; агент получает её признаки без целевых значений и формирует submission CSV. [AIDE, §4.1](https://arxiv.org/html/2502.13138v1)

### Inferences
- **Предлагаемый порядок:** загрузить данные и определить формат submission → сохранить split → выполнить constant baseline → оценить → экспортировать submission → запустить сильный простой baseline из разрешённых библиотек → запустить baker. Для регрессии constant baseline можно реализовать предсказанием среднего train-target для RMSE или медианы для MAE; это проектное решение.
- **Проверка предсказаний:** точное число строк и порядок ID, ожидаемые названия колонок, конечные числа; для вероятностей — диапазон `[0,1]`, согласованный порядок классов и сумма строки около 1. Для ROC-AUC/log-loss явно запрашивать вероятности, а для метрик классов — labels. Стратегия вывода должна входить в контракт задачи; наличие `predict_proba` у baseline подтверждено [документацией](https://scikit-learn.org/stable/modules/generated/sklearn.dummy.DummyClassifier.html).
- **Продвижение победителя:** worker пишет в собственную папку; scheduler проверяет score и файлы, затем атомарно обновляет `best.json`, ссылающийся на неизменяемый артефакт. Только scheduler меняет incumbent; это устраняет гонку, когда два worker одновременно считают себя победителями. Предыдущий лучший файл не удаляется.
- **Финиш:** если остаётся время, refit выбранной конфигурации на всём доступном train и экспортировать в новый файл. Подменять best-output только после успешной проверки нового файла; при сбое оставить уже готовые предсказания. «Всегда есть submission» достижимо после успешного первоначального экспорта; при некорректных входных данных абсолютной гарантии нет.

### Gaps
- Без точной метрики, класса positive label и sample-submission нельзя окончательно определить выходную схему и выбрать правильный constant baseline.
- На этапе исследования код не запускался; совместимость конкретных версий Python 3.12 и разрешённых библиотек не проверена.

## Как ограничить утечки, случайность и расход ресурсов?

### Takeaway
Достоверность сравнений важнее числа гипотез: фиксированные splits и metric harness, воспроизводимые записи, контролируемая параллельность и резерв на финальный экспорт. Качество на многократно используемой validation нельзя выдавать за независимую оценку. [scikit-learn: leakage/randomness](https://scikit-learn.org/stable/common_pitfalls.html)

### Cited Findings
- Scikit-learn рекомендует разделять данные до preprocessing, обучать преобразования только на train и использовать Pipeline; подглядывание в test даёт оптимистичную оценку. Для сопоставимых folds документация рекомендует фиксировать random seed splitter; RNG модели также влияет на результат. [Common pitfalls](https://scikit-learn.org/stable/common_pitfalls.html)
- RD-Agent в отчёте использовал **24 часа, 12 vCPU, 220 GB RAM и V100**, а не три часа на CPU. Результаты усреднялись по нескольким seed; отчёт называет результаты предварительными. Переносить его benchmark-цифры на наш бюджет нельзя. [RD-Agent, §3–4](https://arxiv.org/html/2505.14738v1)

### Inferences
- **Validation:** один `split_id` и одинаковые индексы для всех кандидатов; тип split задавать задачей (stratified/group/time при необходимости). Защитить metric harness от изменений worker. Последний holdout, если он нужен для честного отчёта, не использовать для baker и selection; его labels хранить вне доступа worker. Pipeline уменьшает preprocessing leakage, но не решает переобучение на validation после множества адаптивных попыток. Основание: [scikit-learn](https://scikit-learn.org/stable/common_pitfalls.html).
- **Случайность:** стартовый поиск на одном фиксированном seed экономит время, но небольшой выигрыш может быть случайностью. Проверять только финальных 1–2 претендентов на заранее выбранных дополнительных seed, если бюджет позволяет; хранить все результаты, не выбирать удобный seed. Фиксировать версии зависимостей, hash данных/кода/split, промпт, модель API и параметры генерации. Это проектная политика воспроизводимости, не гарантия побитового совпадения Qwen API.
- **8 CPU / 32 GB:** начать с двух worker и двух computational threads на worker, оставив запас контроллеру и памяти. Ограничить также BLAS/OpenMP threads. Параллельность увеличивать только после замера реального RSS и длительности; число процессов не равно доступной вычислительной мощности. Это консервативная стартовая настройка, не доказанный оптимум.
- **Если три часа — бюджет исполнения, предлагаемые лимиты:** 15 минут на данные и baseline, до 135 минут на поиск, 30 минут на подтверждение победителя/refit/export. Начать с 3–5 минут на train-кандидата, максимум одной repair-попытки и явных лимитов wall-clock, API-calls/tokens и числа экспериментов. Не запускать новый train, если оставшегося времени недостаточно для train + export. Точные числа следует откалибровать первым baseline; ограниченный эксперимент заимствован из [autoresearch](https://github.com/karpathy/autoresearch/blob/master/program.md).
- **Контекст и остановка:** полный журнал хранить на диске; в LLM отправлять ограниченную сводку, а не все stdout. Останавливать поиск по deadline, исчерпанию бюджета или серии неулучшающих попыток; при остановке выдавать incumbent и причины. Бесконечный режим autoresearch не соответствует фиксированному времени хакатона. [program.md](https://github.com/karpathy/autoresearch/blob/master/program.md)

### Gaps
- Нет экспериментальной оценки, сколько попыток успеет наш CPU-прототип: неизвестны размер данных, используемые модели, API latency и лимиты провайдера.
- Источники не доказывают преимущество LLM-baker над простой фиксированной очередью моделей при таком бюджете. Это стоит проверять отдельным сравнением с одинаковыми splits и временем.
