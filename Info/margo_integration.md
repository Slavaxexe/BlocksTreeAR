# Соединение подготовки margo с max_pipeline

Ветка `margo` скачана отдельно в `../AlfaHakaton-margo` (commit `1b8931eadf751cdc8cda8131de15b22fd8138feb`). Её исходники не меняются и не копируются поверх нашей ветки. Для обеих частей используется наше окружение: pyproject margo перечисляет только API-зависимости, хотя её обработке нужны также pandas, sklearn, pyarrow и другие пакеты из предоставленного requirements.txt.

## Граница между частями

Мост `agent/margo_handoff.py` читает реальные артефакты margo:

- `input_manifest.json`: исходные файлы, target, ID, **целевая метрика**;
- `output_manifest.json`: готовый split, размеры и схемы parquet;
- `recipe.json`: рецепт преобразований;
- `data_profile.json`, `preparation_report.json`: EDA и отчёт для наших ролей.

Envelope проверяется по реальной схеме margo. Неверные target, метрика, статусы, пересекающиеся индексы или несовпадающий порядок строк отклоняются. Pickle margo не загружается. Мост сохраняет очищенные исходные таблицы, исходный split, рецепт и хеши в `handoff/`; происхождение записано в `provenance.json`.

В margo пока **нет этапа выбора моделей**. Поэтому отдельный JSON обязан передать `selected_models` в нашем формате. Он может также передать ожидаемую `primary_metric`, `submission`, `validation_constraints` и `id_columns` для конфигурации нового запуска подготовки. Метрика из selection не может заменить метрику существующего input_manifest. `tests/fixtures/margo_regression_selection.json` — явный тестовый выбор семейств для интеграционного прогона, а не решение upstream-агента.

## Преобразования и валидация

Готовые train_features и val_features не склеиваются для нового случайного split. Мы проверяем их схемы/строки и используем **тот же внешний split**. Исходные строки и фиксированный рецепт нужны, чтобы переобучить DataTransformer margo внутри каждого inner train-fold и затем на всём train. Медианы, категории и масштабирование не переносятся из валидации в обучение.

Для обычных моделей рецепт является первым sklearn pipeline step, а выбор столбцов backend выполняется уже после него. Для AutoML сначала рецепт обучается только на внутреннем train для поиска; затем выбранный estimator и свежий рецепт обучаются на всём outer-fit. AutoML с внешним рецептом поддерживает внутренний holdout; CV с fold-local recipe поддержана у обычных моделей. В финале новые поиски и новые признаки не создаются: переобучаются сохранённый рецепт и победившая модель. `preparation_fit_rows` показывает фактическое число строк fit преобразований.

ID берутся из исходных CSV со строковым dtype: margo может потерять ведущие нули в своих *_ids.parquet. После удаления строк с плохим target сохранённые исходные индексы переводятся в позиции очищенной таблицы. Исходники внешнего пакета, рецепт и split проверяются по SHA-256.

## Запуск

Полный прогон неизменённой подготовки и нашего обучения, с общим таймером:

```powershell
uv run --locked python run_margo_pipeline.py data/regression --margo-root ../AlfaHakaton-margo --selection tests/fixtures/margo_regression_selection.json --target site_eui --metric rmse --output-dir artifacts/margo-run --time-budget 4800 --preparation-timeout 600 --trial-timeout 180 --max-trials 10
```

Если подготовка уже выполнена, можно передать её выход без повторного запуска:

```powershell
uv run --locked python run_margo_pipeline.py . --margo-root ../AlfaHakaton-margo --prepared-dir path/to/margo-output --selection models.json --output-dir artifacts/from-margo --time-budget 4800
```

API-подключение берётся из нашего Settings/.env, без записи ключей в задания worker. Для LLM-предложений подготовки используется адаптер нашего JSONAgents с HTTP-retry/JSON-контрактом, который реализует интерфейс клиента margo. Флаг `--no-preparation-llm` оставляет детерминированный план margo.

`pipeline_report.json` отражает весь прогон, `training/report.json` — нашу часть; итоговый submission копируется в корень запуска. Каталог запуска должен быть новым. Схема: `python training_viewer.py artifacts/margo-run/training --port 8766`.

## Наследуемые ограничения margo

- Профиль EDA и статистика target строятся по всему train до split. Поэтому выбор рецепта в исходной версии нельзя считать полностью независимым от внешней валидации. Наш мост обеспечивает fit преобразований на правильных подвыборках, но не отменяет уже выполненный upstream-анализ.
- group_column/time_column в margo являются метаданными: случайный split сам их не соблюдает. Мост проверяет фактические индексы и отклоняет небезопасный split; upstream должен передать корректные предзаданные индексы.
- Семейства моделей и метрика не извлекаются агентом margo из task.md автоматически: метрика задаётся её конфигурацией, выбор семейств приходит отдельно.
- Для переноса итоговой модели нужен тот же внешний пакет data_preparation. Изменение его исходников после handoff явно отклоняется; ZIP для платформы с этим внешним модулем требует отдельной сборки.

Проверки границы и реального recipe без API:

```powershell
uv run --locked python -m unittest tests.test_margo_handoff tests.test_margo_recipe -v
```

## Выполненный сквозной прогон

`artifacts/margo-integration-20261023-01` — реальная задача `data/regression`, а не синтетические данные. Общая длительность 314.813 секунды. Margo с одним реальным запросом Qwen создала 76 признаков: 42 646 train / 10 662 validation / 22 449 test. Все пять стартовых моделей отработали без ошибок обучения:

| Семейство | Validation RMSE |
|---|---:|
| Ridge | 53.94205 |
| LightGBM | 44.99830 |
| CatBoost | 46.11110 |
| FLAML | 47.06697 |
| AutoGluon | **44.94407** |

Выбранная базовая модель AutoGluon и внешний рецепт переобучены на 53 308 строках. `submission.csv` содержит 22 449 строк с исходными ID/порядком и конечными предсказаниями. Целевая RMSE пересчитана по сохранённым validation_predictions.csv и совпала с отчётом. Реального test score нет: метки test недоступны. Доказательства сохранены в `verification.json`.

В этом прогоне дальнейший поиск остановился из-за слишком короткого общего бюджета запросов аналитика и планировщика (60 секунд); финальная модель всё равно сформирована. Исправление в нашей ветке: компактный контекст EDA, адаптивный бюджет пары до 180 секунд по измеренным задержкам, адаптивный бюджет финального анализа и явный текст ошибки таймаута. Полный отчёт на диске не сокращается.

Перепроверен только сорвавшийся запрос планировщика с прежним анализом: `role_recovery/verification.json`. Планировщик успешно ответил за 40.188 секунды и выдал пять кандидатов; они не обучались повторно, чтобы сохранить один сквозной прогон. Основной отчёт сохраняет фактическую историческую причину остановки `planning_unavailable`. Утверждать, что полный цикл поиска после исправления был повторно пройден, нельзя.
