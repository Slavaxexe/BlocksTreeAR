# Операции вместо генерации кода

LLM формулирует гипотезу и JSON-план. Python-реализации исполняет наша система.
Это структурированный протокол, а не серия нативных tool_calls к LLM API.

## Эксперимент

Метаданные разбиения используют time_column и group_columns. Старые time-алиасы
split_column/year_column приводятся к time_column без удаления исходного ключа:
готовый исполнитель использует единый time_column, старые метаданные совместимы.
EDA, общий holdout ансамблей и AutoML используют одну реализацию временного и
группового разбиения. AutoML.split_column/group_by позволяют явно задать столбец
внутреннего holdout, не изменяя внешний split.

До основного поиска сохраняется дешёвый mean/mode/prior baseline:
`baseline/submission.csv` в каталоге запуска и итоговый файл рядом с task.md.
Для этого используются загруженные данные и готовая операция constant, без
вызовов Baker/AutoML. После фиксации разбиения node_000 получает независимую
оценку constant по обычному контракту эксперимента.

Начальному EDA выделяется до 15% общего времени (`--eda-fraction 0.15`).
Сначала идут структурные измерения без построчных таргетов; после фиксации
разбиения — проверки признаков небольшими моделями только внутри fit.
По умолчанию доступны два исследовательских слота (`--research-parallel 2`).
При исчерпании времени, вопросов или бюджета API этап заканчивается раньше;
ожидания ради заполнения времени нет. `--eda-fraction 0` отключает этот этап.
`--eda-seconds 1200` задаёт явное окно начального EDA в 20 минут, включая структурные
исследования и уточнение подготовки. Оно действует и при `--research-unlimited`;
после окна начинаются эксперименты, а EDA может продолжаться параллельно.

Основные эксперименты начинаются после начального EDA. Baker получает краткие
выводы и до трёх измеренных улучшений с точными рецептами признаков. Это кандидаты,
а не обязательный набор. Принудительный запуск AutoML на сырых данных после EDA
отключён: LLM сам выбирает модель, набор признаков и бюджет. Дальнейшие исследования
могут продолжаться параллельно в оставшихся исследовательских слотах.

1. Baker выбирает изменение и родителя.
2. Для AutoML — Idea.automl с настройками. Для составного решения — планировщик
   выбирает блоки из каталога operations.CATALOG.
3. Сборщик проверяет связи, сохраняет конфигурации и доверенные обёртки.
4. Worker выполняет smoke/обучение и общую оценку на неизменной внешней валидации.
5. При ошибке LLM исправляет ToolCall; при успехе анализатор возвращает факты Baker.

ToolCall: kind, parameters, inputs, outputs. inputs/outputs переименовывают
канонические ключи операции для нескольких моделей в одной сборке.

Пример операции обучения:

```json
{
  "kind": "fit",
  "parameters": {
    "estimator": "lightgbm.LGBMClassifier",
    "parameters": {"n_estimators": 300, "learning_rate": 0.05},
    "search_space": {"num_leaves": {"kind": "int", "low": 16, "high": 64}},
    "num_trials": 10
  },
  "outputs": {"model": "model_lgbm"}
}
```

Нужны входы fit_features, fit_targets, transformer, fit, preparation. Подбор
выполняется внутри fit, включая повторное обучение преобразований на внутренней
обучающей части. После выбора параметров модель обучается на всём fit.
Внешняя валидация и тест используются только для предсказаний.

## Анализ признаков

ResearchPlan.analyses содержит запросы AnalysisRequest. Выбираются kind, columns,
target, group_by, filters/comparison_filters, sample_rows, estimator и параметры
внутренней валидации. Готовые виды: quality, association, correlation, shift,
groups, redundancy, missingness, interactions, predictive, permutation, ablation,
feature, stability. sample_rows/top_k=null отключают соответствующий выбор подмножества.

Прокси-оценки явно отделены от внешнего качества решения. Новый признак сначала
проверяется внутри fit, затем Baker может включить его в полноценный эксперимент.
Точные измерения кешируются по запросу/подготовке/фазе, независимо от текста гипотезы.

## AutoML

AutoMLPlan управляет models, model_parameters, typed search_space, num_trials,
validation/folds, holdout_fraction, bag_folds/stack_levels, ensemble, budget_fraction,
columns/drop_columns и features. Готовые адаптеры: FLAML и AutoGluon; временные и
групповые схемы для них пока требуют отдельной реализации, обычные модели используют
групповую/временную внутреннюю валидацию при подборе. Внешний split не меняется.

Каталог расширяемый, но конечный: новую неподдерживаемую процедуру добавляет
разработчик, LLM не подменяет её произвольным Python. Протокол чтения/подготовки
новых форматов пока остаётся прежним, с генерируемым preparer-кодом.


## Уточнения после прогона классификации

preprocess.feature_columns задаёт полный набор признаков. Пустой список сохраняет
все признаки; категориальные определяются по dtype. Старое имя columns принимается
как алиас. Фактические selected_columns и unused_created_features пишутся в
preprocess_*_full_diagnostics.json и передаются анализатору и Baker.

Входная таблица предобработки сохраняется в transformer.fit_source_: подбор не
ищет новые признаки в исходном fit. Рецепты признаков и предобработка заново
обучаются внутри внутренней обучающей части. Операция fit пока использует один
holdout; CV доступен через AutoML. Это явно записывается в диагностике вместе
с фактическим числом завершённых испытаний.

Имена моделей AutoML нормализуются под движок: LightGBM → lgbm для FLAML и GBM
для AutoGluon, включая ключи параметров и пространств поиска. Baker и планировщик
получают допустимые идентификаторы. Интерфейсы новых блоков выводятся системой из
операций и aliases. При нескольких обучающих блоках время делится между ними;
жёсткое ограничение всего процесса остаётся общим.

## Объединение готовых решений

Baker может задать Idea.ensemble. План сразу компилируется в saved_ensemble:
отдельный запрос планировщику не нужен. prediction_sources перечисляет завершённые
ноды, качество, доступность вероятностей, готовность внутренних holdout-прогнозов и отличие от лидера.
Матрицы предсказаний в контекст LLM не передаются.

Доступны следующие методы:

| method | Что делает |
| --- | --- |
| mean | Взвешенное среднее готовых численных прогнозов |
| vote | Взвешенное голосование по меткам классов |
| probabilities | Среднее вероятностей с согласованием порядка классов |
| conditional | Меняет веса источников по правилам на исходных признаках |
| stacking | Обучает метамодель на предсказаниях источников |
| gating | Обучает модель, выбирающую веса источников для каждого объекта |

Например, правило меняет источник в зависимости от признака:

```json
{
  "source_nodes": ["node_001", "node_003"],
  "method": "conditional",
  "weights": [0.7, 0.3],
  "rules": [{
    "conditions": [{"column": "feature_a", "operation": "lt", "value": 10}],
    "weights": [0.2, 0.8]
  }]
}
```

Условия одного правила соединяются AND; первое совпавшее правило побеждает.
Без совпадений действуют общие weights. combine задаёт mean/vote/probabilities;
без него система выбирает вероятности, голосование или среднее по типу задачи
и наличию вероятностей. Сами правила и фиксированные веса задаёт Baker.
Подбирать их по меткам внешней валидации нельзя.

Stacking допускает estimator/parameters: линейную метамодель или нелинейную модель
из установленных библиотек со sklearn-интерфейсом. passthrough=true добавляет
исходные признаки, feature_columns выбирает их подмножество. Поэтому метамодель
может учитывать и прогнозы, и их зависимость от свойств объекта.

Gating строит классификатор источников по исходным признакам. Цель — источник
с меньшей ошибкой на внутренней отложенной строке; predict_proba даёт веса моделей
для нового объекта. По умолчанию используется небольшое дерево; можно выбрать
другой классификатор с predict_proba. Для классификации ошибка строки — log loss,
для регрессии — квадрат ошибки или модуль при MAE. Это прокси для выбора эксперта,
а не гарантия улучшения целевой метрики, особенно Macro F1.

При подготовке один раз выделяется общий внутренний holdout: 20% строк fit,
с учётом объявленных групп или времени. Внешняя валидация и тест не меняются.
Базовая модель обучается на оставшихся 80% fit и сразу предсказывает holdout,
внешнюю валидацию и тест. Метки holdout используются только обучаемым объединителем.
Stacking/gating читают сохранённые прогнозы и обучают только метамодель.
Повторного обучения источников и нового поиска AutoML при объединении нет.

Модели и результаты идентичных операций хранятся один раз в training_cache
общего каталога прогона. Блокировка не позволяет двум воркерам одновременно
обучать одну конфигурацию на одинаковых входах. Ноды сохраняют ссылку на кэш.
AutoGluon оставляет победителя с необходимыми зависимостями и одним нативным кэшем данных для refit; smoke-модели удаляются.
FLAML сохраняет победившую модель, преобразователи и категории, без состояния поиска
и копий обучающих таблиц. У обычных моделей сохранённый препроцессор также не содержит fit_source_.
Неизменённые блоки читаются из исходной ноды по проверяемому хешу; при исправлении
создаётся локальная версия. Исходный блок остаётся неизменным.

В каждой ноде сохраняются validation_predictions.csv, test_predictions.csv,
meta_predictions.csv, predictions.json и вероятности в probabilities.npz.
Все прогнозы привязаны к хешам подготовки и реализации. Простые объединения
также сохраняют честные holdout-прогнозы и могут служить источником stacking.
Сам stacking/gating обучался на holdout, поэтому его прогнозы на тех же строках
нельзя использовать для обучения следующего объединителя. Это отмечено meta_held_out=false.
Параметры folds/seed старых ансамблей больше не управляют разбиением.
Старые прогоны без meta-прогнозов доступны в мониторинге; для нового stacking нужен новый прогон.

Для описательных EDA-запросов dataset явно выбирает fit/validation/test.
compare выбирает вторую таблицу только для shift. Проверки с целевой переменной
выполняются внутри fit. Неудачные измерения нельзя указывать как доказательство
исследовательского вывода.

Подробности выражений, native-категорий, подбора весов и финального refit: [upgrades.md](upgrades.md).

## Направления исследования и важность выводов

EDA ведёт учёт направлений: качество данных, сдвиги распределений, зависимости,
единица наблюдения и ключи, преобразования, кодировки, история, проверки небольшими
моделями. До подготовки разбиения доступны первые четыре направления без построчных
меток. Два из трёх назначений исследуют менее изученные направления; третье уточняет
важный активный вывод, если такой есть. Параллельные назначения учитываются сразу.
Это выбор направления, а не готовой гипотезы: признаки, ключи, измерения и рецепты
предлагает LLM. Если предпосылок для направления нет, он объясняет причину и выбирает
новое применимое измерение. Проверять каждый инструмент любой ценой не требуется.

Название вопроса или признака не делает измерение новым. Система сопоставляет
выполняемые запросы, включая выборку, фильтры, параметры и seed. Повтор целого плана
не запускает вычисления и рецензента; в смешанном плане выполняются только новые
проверки. Источник прежнего измерения сохраняется в reuses. После ошибки процесса,
не оставившей измерений, повтор разрешён.

Рецензент указывает importance, confidence и стабильную тему каждого вывода.
Важность отражает влияние на выбор решения, уверенность — силу измеренных
доказательств. Улучшение маленькой модели на внутренней выборке не означает улучшения
на тесте. Отрицательный результат одного ключа не исключает остальные ключи.

Baker получает до восьми важных выводов с краткими фактами и до трёх перспективных
наборов рецептов с условиями их проверки. Мелкие наблюдения и повторения одной темы
не заполняют этот контекст. Исследователь получает до шести открытых вопросов,
сводку покрытия направлений, активные работы и последние четыре завершённые работы.
Полные измерения, выводы и рецепты остаются в каталоге прогона для мониторинга
и отладки; растущий архив целиком в запросы модели не передаётся.

## Сопоставимые проверки EDA

`predictive`, `permutation` и `interactions` применяют переданные рецепты `features`.
Для `feature` прежние рецепты задаются в `baseline_features`, а новые — в `features`.
Совпадающее имя заменяет соответствующий рецепт только в кандидате: так можно
сравнить два значения smoothing, сохранив остальные преобразования. В обоих
вариантах используются одинаковые исходные столбцы и внутреннее разбиение.
Несколько новых рецептов проверяются как один набор, без приписывания общего
улучшения отдельному признаку.

В `ablation` задаются исходные `baseline_columns` и только удаляемые столбцы в
`columns`. Рецепты сохраняются в обеих моделях. Удаляется вход модели: если другой
сохранённый рецепт использует этот исходный столбец, он продолжает его читать.
Чтобы исключить весь источник информации, нужно также перечислить зависимые
выходы рецептов. Пустая итоговая модель отклоняется до обучения.

Результат содержит фактические `feature_columns`, `recipe_names`, хеш внутреннего
разбиения и список изменений. Покрытие историей считается до глобальной подстановки.
Пустые популяции возвращают `unavailable`, ошибки запроса — `failed`; остальные
запросы того же исследования продолжаются. Версия кэша обновлена, поэтому прежние
результаты ошибочных реализаций не используются для новых вычислений.

Проверки нескольких ключей разделяются на отдельные измерения для защиты от
повторов одного ключа под другим названием. Рецензент должен учитывать область
проверки и не отвергать целое семейство решений по одному ключу или произвольному
порогу улучшения.

Мониторинг отдельно показывает исход выполнения и вывод: ошибка любого измерения
окрашивает ноду красным, неопределённость или отсутствие данных — жёлтым,
подтверждённая гипотеза — зелёным. Опровергнутые гипотезы и остановленные работы
показаны серым. Ошибки отдельных измерений перечислены в карточке ноды, включая
старые прогоны; их научные выводы автоматически не пересчитываются.

## Бюджет, обратная связь и справка

`--research-call-fraction 0.3` ограничивает все обращения EDA (план, рецензирование,
повторы) 30% общего числа API-вызовов. При 150 вызовах это максимум 45 на весь прогон,
включая начальный и параллельный EDA. `--research-unlimited` эту квоту не отменяет.
Исследования резервируют вызовы перед запуском и освобождают остаток при завершении.
Резервы модельных нод недоступны EDA. При временной нехватке свободных вызовов
исследования приостанавливаются; при исчерпании своей квоты заканчиваются.
Окно `--eda-seconds` задаёт максимум времени: исчерпание квоты переводит к моделям раньше.

Результаты моделей и их анализ поступают Baker и исследователю; ошибка блока
возвращается реализатору. Справочник API продолжает автоматически подбирать
сигнатуры по выбранной конфигурации и сохраняет ответы lookup_api для следующих
ролей в том же прогоне. Дополнительные вызовы справочника ограничены двумя раундами
на блок за все его исправления.

`agent/guidance.py` содержит отдельные проверенные правила исполнения и анализа:
единицы улучшения метрики, знаменатели entity-статистик, границы выводов о shift,
контракты ablation/groups и различия smoke/full. На запрос выбирается до трёх
релевантных правил, без нового LLM-вызова. Повторные известные ошибки увеличивают
приоритет соответствующей подсказки; счётчики сохраняются в guidance_observations.json.
Правила проверяются разработчиком и остаются между запусками. Неизвестная ошибка
и неподтверждённое объяснение LLM автоматически не превращаются в новую истину.

Исследователь получает компактный профиль (минимум/медиана/максимум и три частых
значения), актуальные выводы и короткую историю. Полные измерения доступны через
каталог анализа. Рецензент получает до четырёх относящихся к проверке прошлых
выводов без повторной передачи их доказательств и всех рецептов. Baker сохраняет
проверенные рецепты и ограничения с компактными численными фактами вместо полных
дублирующихся evidence-блоков. Сохраняются исходная/новая метрика и знаменатели
показателей ключей, чтобы проверять выводы, а не доверять только тексту рецензента.
Текст утверждений не обрезается. Размеры инструкций, схемы и полей контекста
записываются в prompt_characters каждого llm/*.request.json; это символы, не токены.

Отклонение от назначенного направления исследования записывается как замечание
планировщику, без повторного запроса корректного JSON. Неизвестный resolves оставляет
вопрос открытым и записывается в журнал; ссылки на отсутствующие или неудачные
измерения по-прежнему отклоняются. Абсолютное и процентное улучшение вычисляет инструмент.

## Источник истории и обоснование валидации

В проверках с `history` или `target_encoding` сначала выделяется внутренний
holdout на полном доступном fit. Вся внутренняя обучающая часть остаётся источником
статистик. `sample_rows` ограничивает только строки обучения прокси-модели и её
оценки. Метки внутреннего holdout не входят в источник; строки внешней валидации,
теста и общего holdout ансамблей также не добавляются. `inner_reference_rows`
показывает размер источника, `inner_train_rows` — размер обучения модели.
Одинаковые baseline/candidate используют одно разбиение и одни выбранные строки.

Для ключей `repeated_fit_row_fraction` означает повторяемость во всех периодах,
а `within_period_ambiguity_fraction` — долю строк с дублем пары (ключ, период).
Высокая первая доля не доказывает неоднозначность и может быть полезна для истории.
В результате отдельно приводятся числитель и знаменатель неоднозначности.
Совпадение ключа не доказывает, что это один реальный объект.

Профиль вычисляет `ordered_query_ranges` для числовых и временных признаков:
какие диапазоны test полностью выше/ниже диапазонов train. Это измерения,
а не автоматическое правило выбора split. LLM сопоставляет их со смыслом задачи
и записывает `validation.deployment_scenario` и `deployment_reason`. Допустимы
future_period, unseen_groups, exchangeable, uncertain. Обоснованный случайный split
остаётся доступен при сдвиге значений признака. При заявленном future_period
worker проверяет, что validation действительно позже fit; выбранный split
во время поиска моделей не меняется. Названия столбцов и домен не зафиксированы.

## Готовое исполнение SplitPlan

Preparer получает split_catalog и split_contract. LLM возвращает стратегию,
столбцы и параметры в validation; функцию make_split больше не пишет.
Worker вызывает agent.validation.split_rows. Старая сгенерированная make_split,
если осталась в prepare.py, игнорируется. Результат — позиции исходных строк,
независимые от индекса DataFrame и сортировки временного признака.

Готовые стратегии: random, stratified, group, stratified_group, time, group_time,
ordered. Поддержаны fraction/validation_rows, seed, составные group_columns,
stratify_columns, квантильные stratify_bins, validation_periods или cutoff,
gap_periods/gap_rows. rare_class_policy=error/train_only определяет, как поступать
со стратами, которые нельзя поместить в обе части. Стратифицированное групповое
разбиение приближённо соблюдает размер и пропорции классов, сохраняя группы целиком.
group_time удаляет из обучающей части группы из будущей валидации; для панели,
где все объекты повторяются, такой план может быть невыполним.

План и исполнитель сохраняются как validation.split_plan и split_executor=builtin,
позиции — в split.npz. Абсолютный cutoff внешнего split не переносится во внутренние
проверки моделей: они используют свои размеры holdout. LLM выбирает план по
смыслу задачи, а не по жёстко заданным именам признаков. Загрузчик, нестандартная
метрика и формат записи результата пока остаются генерируемыми функциями.


## Полный fit и переход EDA → эксперимент

Обычная модель и исследователь получают весь outer-fit. Общий внутренний holdout
ансамблей сохраняется как набор индексов, но его строки заранее не исключаются
из обучения каждой модели. Простые смеси используют готовые прогнозы. Для
stacking/gating и подбора весов недостающие метапрогнозы строятся отдельным обучением
только на inner-train, без меток meta/outer-validation/test. Это дополнительная работа
при первом запросе; метапрогнозы и обученные операции кешируются в рамках прогона.
Обученные комбинаторы не объявляются честными источниками следующего уровня stacking.

EDA-кандидаты имеют устойчивые ID и состояния untested/pending/tested/failed,
определяемые по реально исполненным рецептам. Baker выбирает feature_candidate_ids
или объясняет defer/reject в feature_decisions. Выбранные рецепты сохраняются в
гипотезе; планировщик получает их независимо от сокращения текстовых выводов EDA.
Сборка проверяет точное наличие выбранных рецептов. Для native AutoML они добавляются
в features адаптера. Решение о выборе признаков и модели остаётся у LLM.

Родителями могут быть все успешно завершённые модели, включая ещё анализируемые.
Ошибка ответа Baker допускает до трёх последовательных запросов с актуальными
результатами и предыдущей ошибкой; исчерпание квоты ключа повторов не вызывает.


## Выделенные AutoML-эксперименты

После начального EDA и рабочего baseline очередь один раз резервирует по одному
эксперименту на каждый установленный адаптер: FLAML и AutoGluon. Они занимают обычные
слоты моделей, имеют приоритет и не снимаются Baker при смене лидера или удалении
обычной идеи. `--no-automl` отключает это резервирование. Ограничения общего времени,
API и числа нод продолжают действовать.

Роль automl_planner получает компактный профиль, выводы и рецепты EDA, операции
текущего родителя, возможности только назначенного адаптера и бюджет ноды. LLM
выбирает AutoMLPlan: набор признаков, преобразования, модели, параметры и поиск.
Данные, названия столбцов и семейство модели не зафиксированы разработчиком.
Конфигурация проходит ту же типизацию и затем исполняется штатным адаптером.
При ошибке планирования сохраняется предупреждение и остаётся попытка с безопасными
настройками этого адаптера. Последующие улучшения и объединения снова выбирает Baker.

## Перепроверка финалистов

После закрытия поиска до трёх лучших завершённых решений проходят два общих
дополнительных разбиения внутри исходного fit. Сохраняется выбранная стратегия:
для времени используются предыдущие временные окна, для групп — новые групповые
holdout, для случайного/стратифицированного split — другие seed. Основной split
и его оценки не меняются. Если корректных дополнительных разбиений меньше двух,
этап пропускается.

Конфигурации фиксируются; LLM и AutoML-поиск не вызываются. Модели обучаются заново
без проверочных строк. Обучаемые combiner и веса ансамблей переобучаются на
внутренней отложенной части каждого нового fit; старый обученный combiner не загружается.
Старые пайплайны без безопасного фиксированного refit не участвуют.

Претендент заменяет лидера, если не хуже на каждом новом split и имеет лучший
средний результат с учётом исходной валидации. Отсутствующие результаты нельзя
засчитывать как улучшение. Если лидер не завершил оба split, он сохраняется.
Результаты не возвращаются Baker, поиск после проверки не возобновляется.

`--final-validation-seconds 600` резервирует до 600 секунд, не больше 10% общего
времени. `0` отключает этап. `--validation-finalists 3` и `--validation-folds 2`
задают число кандидатов и разбиений. Резерв входит в общий лимит и отделён от
`--final-refit-seconds`. Отчёт, оценки и индексы находятся в `final_validation/`;
временные обученные модели удаляются. При ошибке сохраняется предыдущий сабмит.

Это проверка устойчивости, а не независимый тест: данные исходного fit уже
использовались для EDA и выбора конфигураций. Среднее и разброс не являются
несмещённой оценкой качества или доказательством статистической значимости.

## Готовые сборки и наследование

Исполнимые рецепты сохраняются в `builds/<id>.json`. `eda_<hash>` содержит
фактический набор признаков, предобработку и параметры модели успешной проверки
feature/ablation. Для готовой сборки нужен весь целевой набор задачи и проверка
без фильтрации популяции. Рецепт подгруппы без fallback не объявляется полным решением.
`node_...` фиксирует фактически выполненные операции завершённого эксперимента.
Выбранные при настройке параметры замораживаются; AutoML использует `reuse_node`
для refit сохранённого выбора с тем же алгоритмом предобработки без нового поиска.

Baker получает короткие карточки `ready_builds`. Для проверки EDA достаточно
гипотезы и `build_id`; отдельный node_planner не вызывается. Модель обучается
на всём основном fit и оценивается на внешней валидации, поэтому внутренний
скор EDA не обещается воспроизвести численно.

Для изменения родителя задаются `build_id` и `changes`. `edits` рекурсивно
объединяет только названные параметры, `features` добавляет/заменяет рецепты,
`feature_parameters` меняет отдельные параметры существующего рецепта,
`remove_features` явно удаляет рецепты. Неназванные настройки сохраняются.
При добавлении признака явный список входов preprocess дополняется автоматически.
Новые этапы задаются через `insert` и полный `order`, удаление — через `remove`.
Замена семейства модели требует явного удаления/вставки fit, чтобы не переносить
несовместимые параметры. При обычном improve без готового изменения планировщик
возвращает только AssemblyChanges к сохранённой сборке родителя.

Сборщик проверяет связность интерфейсов и неизменность рецепта по хешу. Источник
и явные изменения записываются в гипотезу ноды. Старые файлы сборок не переписываются;
новые ноды регистрируются отдельно. Для новых архитектур остаётся свободный
планировщик готовых операций; существующими сборками поиск не ограничен.
