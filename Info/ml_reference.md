# Справочник API

Справочник хранится в корневых `.py`-файлах и работает без интернета и Qwen.
Он не содержит условий датасетов, обученных моделей или ключей.

Файлы для работы:

- `ml_reference.py` — lookup, поиск и выбор небольшого контекста для роли.
- `ml_reference_tools.py` — нативные инструменты `search_api`/`lookup_api`, их аргументы и ограничение ответов.
- `ml_reference_data.py` — сгенерированные сигнатуры, docstring, параметры и версии.
- `ml_reference_notes.py` — покрытие пакетов и проверенные пояснения, примеры и ограничения.

`build_ml_reference.py` пересобирает данные из установленных библиотек. На платформе
пересборка не требуется: достаточно положить четыре файла справочника в корень ZIP
вместе с остальными модулями решения и исходным `requirements.txt` организаторов.
Сам справочник не преобразует пакет `agent` в плоскую сборку всего решения.

## Источники и kwargs

Сигнатуры извлекаются через `inspect.signature`, без создания моделей и вызовов
`fit`. Для C-функций, не поддерживающих introspection, отдельно сохраняется первая
сигнатура из docstring, если она есть. Отсутствие сигнатуры явно обозначается.

Документированные параметры разбираются из NumPy/Google-style docstring. Поле
`declaration` сохраняет исходную строку: это может быть тип или краткое описание,
поэтому справочник не выдаёт её за машинно проверенную аннотацию типа.
Длинные описания ограничены по длине; полный исходный docstring доступен в установленной
библиотеке. `source` содержит путь внутри пакета, строку и хеш исходника, если Python
позволяет его прочитать. Версия и лицензия дистрибутива сохранены отдельно.

Для сложных API дополнительно используются:

- AutoGluon: вложенная документация `**kwargs` и имена из словарей реального валидатора.
  Вложенные поля не смешиваются с аргументами верхнего уровня.
- XGBoost: сигнатуры базовых классов, которым конструктор передаёт `**kwargs`.
- LightGBM: нативный движок установленной версии сообщает распознаваемые параметры
  и их алиасы. Их применимость зависит от задачи и сочетания настроек.
- LightAutoML: сохранены вложенные настройки из установленного `tabular_config.yml`.
  Этот YAML уже входит в пакет; в ZIP решения отдельный YAML не нужен.
- FLAML: отдельно описаны настройки AutoML и аргументы, пересылаемые выбранному estimator.

`kwargs_complete=False` означает, что справочник не обещает исчерпывающий список
разрешённых аргументов. Неизвестный параметр при наличии `**kwargs` не объявляется
автоматически ошибкой. Отсутствующая запись не запрещает использовать библиотеку.

Пояснения в `GUIDANCE` отделены от автоматически извлечённых фактов. У них указаны
официальные источники и версия проверки. Если фактически установленная версия
отличается от снимка или версии пояснений, это видно в ответе.

## Использование

Из корня проекта:

```powershell
.\.venv\Scripts\python.exe ml_reference.py catalog
.\.venv\Scripts\python.exe ml_reference.py search "AutoGluon fit time_limit"
.\.venv\Scripts\python.exe ml_reference.py lookup flaml.AutoML.fit --parameter metric
.\.venv\Scripts\python.exe ml_reference.py lookup autogluon.tabular.TabularPredictor.fit --parameter num_bag_folds
.\.venv\Scripts\python.exe ml_reference.py lookup xgboost.XGBClassifier --parameter eval_metric
.\.venv\Scripts\python.exe ml_reference.py lookup lightgbm.LGBMClassifier --parameter is_unbalance
.\.venv\Scripts\python.exe ml_reference.py lookup lightautoml.automl.presets.tabular_presets.TabularAutoML --parameter general_params.use_algos
```

Из Python:

```python
from ml_reference import lookup, search, context_for

api = lookup('catboost.CatBoostClassifier.fit', parameter='time_left')
matches = search('early stopping', package='xgboost')
context = context_for('LightGBM custom multiclass objective', max_chars=12000)
```

Возможные статусы параметра:

| Статус | Значение |
|---|---|
| `explicit` | Есть в реальной сигнатуре |
| `validated_kwarg` | Найден в валидаторе установленного API |
| `delegated` | Есть в базовом API, которому передаются kwargs |
| `native_conditional` | Имя распознаётся нативным движком; применимость условная |
| `documented` | Есть в документации |
| `configuration_default` | Есть во вложенном конфигурационном словаре |
| `unknown_kwargs` | Не найден, но API принимает kwargs; вывод о запрете не сделан |
| `unknown_signature` | Introspection недоступна |
| `not_in_signature` | Нет в доступной сигнатуре без kwargs |

## Передача агентам

Планировщик получает справку по выбранной идее (до 12 тысяч символов). Если идея
не называет API, используется модель родителя. У реализатора и анализатора сначала
подбирается API запланированной модели, затем дополнительные упоминания и исходники.
Полные имена и алиасы импортов распознаются отдельно; неоднозначное короткое имя
вроде Categorical само по себе не добавляет карточки всех библиотек. Фиксированного
приоритета AutoML-библиотек перед выбранным алгоритмом нет.

При нехватке места необязательные разделы карточки исключаются целиком с отметкой
omitted_sections; сигнатура не обрывается. Реализатор и анализатор получают начальную
выборку справки (реализатор до 5 тысяч символов, анализатор до 6 тысяч).
Реализатору и анализатору неуспешной ноды доступны два нативных инструмента:

- `search_api(query, package=None, limit=4)` ищет по английским именам/ключевым словам;
  возвращает до 6 совпадений с точными именами API и сигнатурами.
- `lookup_api(symbol, parameter=None)` возвращает сигнатуру, версии, kwargs и пояснения;
  `parameter` запрашивает конкретный аргумент или вложенный путь настройки.

При первой реализации разрешён один раунд; при исправлении кода и анализе
неуспешной ноды — до двух. Успешные ноды анализируются без инструментов.
В раунде до трёх инструментов; общий бюджет результатов — 5 тысяч символов. Длинные необязательные
разделы исключаются целиком с `omitted_sections`, сигнатуры и JSON не обрываются.
Если нужно, лучше запрашивать один конкретный параметр. Невалидные аргументы и
неизвестное имя функции возвращаются как ошибка инструмента внутри того же диалога.

Клиент передаёт `tools`, обрабатывает `message.tool_calls`, исполняет локальную функцию,
добавляет ответ assistant и сообщения `role=tool` с `tool_call_id`, затем продолжает
запрос к Qwen. После лимита справки или при последнем доступном API-вызове передаётся
`tool_choice=none`: модель должна закончить ответ. Финальный Program/Analysis
по-прежнему проверяется обычной схемой. Baker и планировщик инструменты не получают.

Продолжение после справки не создаёт ноду, не запускает обучение и не расходует
версию блока или повтор валидации JSON. Каждое обращение к Qwen учитывается в общем
лимите API, локальном бюджете роли и общем дедлайне. Локальный лимит реализатора и
анализатора увеличен на эти продолжения; общий лимит запуска не увеличивается.
Thinking сохраняется: у анализатора medium, у реализатора medium при исправлении.

В `llm/NNNN.response.json` сохраняются нативные tool_calls, в `llm/NNNN.tools.json` —
аргументы и результаты. Событие `api_reference_completed` отличает справку от выдачи
финального кода; номер `reference_round` отделён от попытки исправления JSON.

Один и тот же API под альтернативными именами использует общие описания и пояснения.
Повторяющиеся унаследованные методы хранятся один раз с сохранением всех имён.
Данные загружаются один раз; обычная справка не импортирует тяжёлые ML-пакеты.

Справочник исправляет недостаток информации об API. Он не доказывает успешное
обучение, правильность собственного градиента или причину изменения качества.

## Пересборка и проверка

```powershell
.\.venv\Scripts\python.exe build_ml_reference.py
.\.venv\Scripts\python.exe build_ml_reference.py --verify
```

Генератор импортирует доступные библиотеки, извлекает описания, устраняет дубли
и проверяет ключевые API. Обучение, установка зависимостей и обращения к API не
выполняются. Для пересборки нужен полный набор `baseline/requirements.txt`.
Ошибки необязательных модулей сохраняются в `BUILD_ISSUES`; их нельзя трактовать
как запрет всех функций соответствующей библиотеки. LightAutoML может предупреждать
об отсутствующих NLP extras: для табличного API они не требуются.

При добавлении новой библиотеки или функций изменяются `MODULES`/`SYMBOLS` в
`ml_reference_notes.py`, затем выполняется пересборка. Общие замечания добавляются
в `GUIDANCE` с источником и версией; особенности конкретного датасета туда не входят.

## Покрытие текущего снимка

В снимке 29,874 имён API из 38 установленных пакетов; 7,788 уникальных описаний. Имена включают классы, функции, методы и свойства; это не число разных алгоритмов.

| Пакет | Версия | Записей с учётом имён |
|---|---|---:|
| autogluon.tabular | 1.3.1 | 702 |
| lightautoml | 0.4.2 | 1556 |
| flaml | 2.3.6 | 730 |
| catboost | 1.2.8 | 344 |
| lightgbm | 4.6.0 | 228 |
| xgboost | 2.1.4 | 288 |
| optuna | 4.2.1 | 491 |
| torch | 2.5.1 | 12410 |
| scikit-learn | 1.5.2 | 2138 |
| scipy | 1.12.0 | 6788 |

Это широкий выбранный набор API, а не обещание индексации каждого объекта всех библиотек. Все записанные сигнатуры получены автоматически; ручные пояснения охватывают частые сложные случаи.

При сборке ошибок извлечения не было (`BUILD_ISSUES=[]`). Проверены реальные параметры FLAML, AutoGluon, CatBoost, LightAutoML, XGBoost и Optuna, вложенные kwargs AutoGluon, делегирование XGBoost, нативные алиасы LightGBM, версия данных и наличие источников пояснений.

Отдельно просмотрены причины прошлых сбоев: `time_left`, `balanced_subsample`, `class_weights=Balanced`, неверный HPO-словарь, путаница `metric/eval_metric`, исчезающие категории и форма multiclass-градиентов. Обучение и запросы к Qwen при проверке не запускались.
