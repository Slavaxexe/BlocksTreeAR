# Отдельная часть: обучение и валидация регрессии

Этот компонент получает готовый отчёт другого агента с выбранными моделями и EDA. Он не читает task.md для постановки задачи, не выбирает новые семейства моделей, не строит новые признаки и не добавляет этап бизнес-модели. Импутация, кодирование категорий и масштабирование входят в обучаемый pipeline и выполняются внутри обучающих разбиений.

## Входной JSON

Пример: [random.json](../tests/fixtures/training_component/random.json). Формальная схема: `schemas/traininginput.schema.json`. Пути train/test/sample_submission разрешаются относительно файла отчёта; абсолютные пути также допустимы.

```json
{
  "schema_version": 1,
  "task_type": "regression",
  "files": {"train": "train.csv", "test": "test.csv", "sample_submission": "sample_submission.csv"},
  "target": "y",
  "id_columns": ["id"],
  "primary_metric": "rmse",
  "selected_models": [
    {"family": "ridge", "rationale": "Линейный baseline", "parameters": {}},
    {"family": "lightgbm", "rationale": "Нелинейные зависимости из EDA", "parameters": {}}
  ],
  "eda": {"rows": 600, "findings": ["Нелинейность и пропуски в численных признаках"]},
  "validation_constraints": {"strategy": "random", "group_columns": [], "time_column": null},
  "submission": {"filename": "submission.csv", "prediction_column": "prediction"}
}
```

Поддержаны метрики `rmse`, `mae`, `mse`, `r2`, `mape`. Направление фиксируется кодом: максимум только для R². Test не должен содержать target; значения из sample_submission не используются как ответы. EDA должен описывать обучающие данные и не содержать скрытые метки.

`primary_metric` — обязательная целевая метрика из задания, которую определяет и передаёт предыдущая часть пайплайна. Этот компонент и его Qwen не выбирают её заново. Без неё вход отклоняется; неизвестная метрика также отклоняется явно, без замены на RMSE или MAE. Все кандидаты сравниваются по переданной метрике на одном внешнем разбиении. Вспомогательные метрики и функция потерь обучения не меняют критерий выбора победителя. MAE/RMSE в синтетических примерах служат только демонстрацией входного контракта.

Поддержанные family: `ridge`, `elasticnet`, `sgd`, `random_forest`, `extra_trees`, `hist_gradient_boosting`, `lightgbm`, `catboost`, `xgboost`, `mlp`, `flaml`, `autogluon`. Другие имена отклоняются явно, а не заменяются произвольной моделью. В отчёте можно перечислить несколько конфигураций одного семейства.

## Последовательность

1. Проверка контракта, путей, наличия/конечности target и входных таблиц.
2. Qwen получает отчёт, EDA, requirements.txt и установленные версии. Выбирает долю внешней валидации и необходимость CV. Обязательные group/time ограничения берутся из входа.
3. Код создаёт и сохраняет одно внешнее разбиение для всех экспериментов. Разбиение и исходные данные связываются SHA-256.
4. Планировщик Qwen предлагает начальные конфигурации только переданных моделей. Обосновывает параметры, регуляризацию, оптимизатор и оценивает длительность. На каждую переданную модель нужен эксперимент или явная причина пропуска. Сначала планируется одна конфигурация каждого запланированного model_index. Дополнительные начальные варианты передаются как предложения для следующих раундов.
5. Worker проверяет параметры и выполняет реальное обучение в отдельном процессе. CV остаётся внутри outer-fit; преобразования отдельно обучаются внутри каждого fold. В режиме holdout обычных моделей используется внешняя отложенная часть; отдельный внутренний holdout-score не заявляется.
6. Аналитик Qwen отдельным запросом получает реальные score/ошибки/train-validation gap. Возвращает наблюдения, гипотезы, риски и рекомендацию. Планировщик другим запросом получает этот анализ, EDA, шаблоны и оставшийся бюджет; предлагает следующие конфигурации или остановку. Контракты ролей различны. Результаты worker принимаются только при совпадении входов, метрики и split. Ошибка одного кандидата не отменяет остальные.
7. Победителя выбирает код по первичной метрике. Метрика, split и выбранное семейство не меняются агентом после сравнения.
8. Сохранённый рецепт победителя загружается и переобучается на ВСЕХ размеченных строках. Нового поиска моделей на финале нет. Для обычных моделей заново обучается также preprocessing; выбранные итерации/регуляризация сохраняются. Записываются итоговая модель и submission.

## Аналитик, планировщик и координатор

`agent/training_roles.py` содержит две роли с отдельными запросами к одной настроенной модели Qwen:

- Аналитик → `TrainingAnalysis`: `observations`, `hypotheses`, `risks`, `recommendation`, `rationale`. Не возвращает исполняемые конфигурации.
- Планировщик → `TrainingPlan` для старта либо `TrainingNextPlan` для следующих опытов и исправлений. Выдаёт параметры и `estimated_seconds`, не выдумывает измеренный score.

`agent/training_coordinator.py` — детерминированный координатор, не третья LLM. Он выбирает победителя строго по переданной метрике, отклоняет повторы и опыты, не помещающиеся в поисковый бюджет, и сохраняет резерв финального обучения. Для оценки длительности учитывает прогноз планировщика, фактическое wall time последних успешных опытов этого семейства с запасом и жёсткий trial timeout. Прогноз — эвристика; реальный таймер worker остаётся обязательным.

Поиск останавливается по времени, max_trials, решению планировщика, отсутствию новых кандидатов, недоступности API или отсутствию существенного улучшения в двух завершённых раундах. По умолчанию существенный прогресс — больше `1e-4 * abs(score в начале раунда)`. Этот порог используется только для остановки: сам победитель всегда выбирается по точному score. Настройки: `--patience-rounds` и `--relative-min-improvement`.

Отдельный финальный запрос аналитика не меняет победителя и не начинает новый поиск. История ролей, пропуски и причина остановки видны в `report.json`. Ответы сохраняются отдельно: `analysis_XX.json`, `plan_XX.json`, `repair_analysis_XX.json`, `repair_plan_XX.json`, `final_analysis.json`. Схемы: `schemas/traininganalysis.schema.json` и `schemas/trainingnextplan.schema.json`.

SGD/Adam/Nesterov не перебираются для деревьев. Для совместимых моделей Qwen задаёт реальные параметры estimator (`solver`, `loss`, `learning_rate`, `average`, `momentum` и др., когда они поддержаны); текстовые поля optimizer/regularization только объясняют решения. Некорректные параметры возвращаются как ошибка для следующей гипотезы. Для LightGBM поддержана нормализация распространённых нативных алиасов; исходные имена категориальных столбцов в categorical_feature не принимаются после one-hot кодирования.

## AutoML и финал

FLAML сохраняет фактически выбранный estimator и преобразования; финал переобучает их, не запускает ещё один широкий AutoML-поиск. AutoGluon в этом компоненте выбирает одну базовую модель, ансамбли отключены. Его обученный feature generator остаётся замороженным, выбранная базовая модель обучается на всех строках с зафиксированными параметрами и числом итераций. Это отличается от прежнего универсального AutoGluon-пути проекта.

## Исполняемые шаблоны для Qwen

Шаблоны используют только библиотеки из предоставленного `requirements.txt`:

- `agent/training_template_sklearn.py`: Ridge, ElasticNet, SGDRegressor, RandomForestRegressor, ExtraTreesRegressor, HistGradientBoostingRegressor, MLPRegressor.
- `agent/training_template_boosting.py`: LightGBM, CatBoost, XGBoost.
- `agent/training_template_automl.py`: настройки адаптеров FLAML и AutoGluon.

Реестр `agent/training_templates.py` передаёт Qwen фактический Python-исходник шаблона, пример параметров и версии библиотеки. Передаются только семейства из входного selected_models и только когда пакет одновременно разрешён requirements.txt и установлен. Снимок контекста сохранён в model_templates.json; хеш связывает его с текстом функции.

Worker использует эти же шаблоны, поэтому это исполняемый источник, а не отдельные примеры кода. Qwen адаптирует параметры через JSON, не переписывая файлы и общий цикл обучения/валидации. Значения примеров не ограничивают поиск: доступны все параметры, которые принимает и проверяет существующий backend, кроме зафиксированных ресурсов и инфраструктуры. Preprocessing, целевая метрика, разбиение, таймер и финальное обучение остаются ответственностью backend. Шаблоны не добавляют новых обязательных преобразований или ограничений параметров. Они уменьшают необходимость придумывать API, но сохранение или рост качества нужно измерять на задачах.

## Таймер и ошибки

После фактического падения worker аналитик сразу получает параметры, тип ошибки и traceback. Планировщик использует его диагноз и может предложить одну исправленную конфигурацию той же модели; повтор запускается перед остальной очередью. Не более двух таких разборов за запуск; пара запросов ограничена 60 секундами и общим поисковым бюджетом. Новая пара анализа/планирования допускается только с запасом времени на последующий опыт. Повторы входят в `max_trials`. История сохраняется в `report.repairs` и отдельных файлах обеих ролей. Недоступность API не отменяет другие уже запланированные кандидаты и финальное обучение имеющегося победителя.

Qwen в этом компоненте выдаёт типизированный JSON, а не Python-код: проверяются JSON-контракт, параметры estimator, фактическое выполнение, метрики и формат предсказаний. Автоматического переписывания исходного кода backend при программном дефекте нет.

Один таймер начинается до чтения данных и API. По умолчанию общий бюджет 4800 секунд, на финал резервируется 25%, максимум 1200 секунд. API, подготовка планов, обучение, CV, прогноз и запись входят в бюджет. Родитель прерывает worker и его дочерние процессы при превышении времени. Обычная модель ограничена двумя CPU.

Если очередной запрос анализа Qwen не удался, компонент прекращает поиск и всё равно пробует финальное обучение имеющегося победителя. Если финал не успел/упал, сохраняется резервный submission лучшей модели, обученной только на outer-fit; статус `partial` явно отличает его от успешного полного обучения. Успех не обещается при бюджете, которого не хватает даже на один эксперимент.

## Запуск и интеграция

Живая схема одного запуска (каталог может ещё не существовать):

```powershell
uv run --locked python training_viewer.py artifacts/my-training --port 8766
```

Откройте `http://127.0.0.1:8766/`. Схема читает состояния координатора, результаты экспериментов и решения Qwen каждую секунду. Исходники и API-ключи не публикуются.

```powershell
uv run --locked python train_validate.py path/to/input.json --output-dir artifacts/my-training --time-budget 4800 --trial-timeout 300 --max-trials 12
```

Программный вход: `await agent.training_component.run_training(input_path, output_dir, ...)`. Каталог output_dir должен быть новым. Возвращается отчёт; итоговый файл указан в `report['submission']`. Компонент не перезаписывает исходные данные. Доступны JSON-артефакты: `validation_decision.json`, `training_plan.json`, `analysis_*.json`, `final_analysis.json`, `report.json`, `split.npz`, `trials/*/result.json`, `final/result.json`, `final/model.joblib`, `submission.csv`.

Старый `solution.py task.md` остаётся отдельным полным конвейером. Новый train_validate.py — вход именно для интеграции с другим агентом, а не автоматическая замена платформенного интерфейса.

Настоящий Qwen получил синтетический отчёт с Ridge, LightGBM, Random Forest, EDA и RMSE. Выполнено шесть конфигураций на одном 480/120 разбиении, затем полный refit на 600 строках, submission из 200 строк. Весь запуск занял 71,875 секунды при лимите 300.

| Семейство | Лучшая validation RMSE |
| --- | ---: |
| Ridge | 11,6728 |
| Random Forest | 3,8923 |
| LightGBM | **1,5389** |

После окончательного выбора отдельный offline oracle, недоступный компоненту, оценил финальные предсказания: synthetic test RMSE **1,2421**. Это результат искусственного датасета, не платформенный скор. Эта оценка не возвращалась в поиск и не использовалась для выбора победителя. Артефакты: `artifacts/training-component-random-20261023-02`.

Локальные интеграционные тесты выполняют настоящие модели/worker и проверяют group/time CV, изоляцию неверных параметров, full-data refit, строковые ID, API-сбой после обучения, максимум для R² и hard timeout. Отдельно проверены реальные FLAML RF/CatBoost и AutoGluon RF evaluate→final на смешанных численных/категориальных данных; эти проверки используют другие небольшие датасеты, их score нельзя напрямую сравнивать с таблицей выше. Устранены ошибки кодирования категорий FLAML и передачи параметров CatBoost.

Отдельный запуск с настоящим Qwen получил реальную ошибку `Ridge(alpha=-1)`, предложил `alpha=0.1`, успешно повторил обучение и выполнил полный refit на 600 строках. Групповая validation MAE — 2,2710; длительность 28,375 секунды. Это другой набор данных и другая метрика, не сравнение с RMSE выше. Артефакты: `artifacts/training-qwen-repair-20261023-01`.

Сохранённые обученные объекты основного запуска дополнительно проверены: StandardScaler победителя видел 480 строк на оценке и 600 после final. Файл `fit_row_evidence.json` фиксирует это отдельно от заявленного количества входных строк.

Полный запуск с раздельными ролями: `artifacts/training-roles-full-20261023-01`, вход `artifacts/training-roles-full-input.json`. Это синтетический upstream-отчёт с Ridge, LightGBM, RandomForest, FLAML и AutoGluon. Лимит 4800 секунд, trial timeout 120 секунд, max_trials=12. Выполнены 12 успешных опытов за 129.484 секунды; остановка по max_trials. Начальная лучшая RMSE 1.3437629, итоговая 1.2422846 на том же внешнем split 450/150. Победитель переобучен на всех 600 строках, submission содержит 200 прогнозов. Независимая синтетическая test RMSE после завершения поиска — 1.2222229; этот score не передавался ролям.

В `verification.json` проверены реальная передача JSON аналитика следующему планировщику и сохранённые scaler: 450 строк до финала, 600 после. Было 7 запросов Qwen: два начальных планировщика, два цикла аналитик→планировщик, финальный аналитик. После успешного сохранения обучения возникла ошибка печати символа `≈` в Windows cp1251; CLI переведён на UTF-8, исправление вывода проверено отдельно. Это один интеграционный запуск, а не доказательство превосходства архитектуры на других данных.
