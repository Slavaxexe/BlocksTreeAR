# Архитектура: исследование и эксперименты через готовые инструменты

Контроллер читает задание и фиксирует подготовку. Baker формулирует гипотезы,
планировщик собирает операции, worker исполняет готовые реализации. LLM не пишет
Python для EDA или экспериментов. Он выбирает признаки, алгоритмы, параметры,
поисковые пространства и исправляет конфигурации. Дерево нод, заимствование блоков,
анализатор и общий выбор лидера сохранены. Протокол: [operations.md](operations.md).
Первичный загрузчик/подготовка данных пока создаются прежней ролью preparer.

## Поток работы

task.md → извлечение JSON → структурный EDA (если включён) → фиксированная
подготовка/split → простой предиктор → готовые AutoML-кандидаты и гипотезы Baker.
Каждая гипотеза → план операций → сборка → smoke → полный запуск → метрика и
submission → анализатор → следующий вызов Baker. Фоновый EDA публикует краткие
проверенные измерениями наблюдения. Все этапы используют общий дедлайн.


## Общая подготовка

Корень входных файлов — каталог переданного Markdown. Имена файлов, target,
метрика и формат ответа определяются по условию, а не по двум публичным датасетам.

Четыре extractor-запроса извлекают problem, data, metric, output с цитатами.
Цитаты проверяются по исходному тексту и сохраняются в extraction.json.

LLM создаёт один prepare.py на запуск:

- load_data(task_directory, config): читает train/test и дополнительные таблицы;
- score(reference, predictions, config): вычисляет именно заданную метрику;
- write_submission(test, predictions, tables, config, path): пишет требуемый файл.

Python исполняет подготовку, измеряет профиль, сохраняет split.npz, хеши входов и
preparation.json. Ноды используют одинаковые split, scorer и writer. Изменять их
внутри гипотез нельзя. Подготовка имеет первую попытку и два исправления.

LLM выбирает split по смыслу задачи: какую ситуацию должна проверять валидация.
Наличие колонки даты или похожего на группу признака само по себе не требует
временного или группового разделения. LLM выбирает декларативный SplitPlan из
переданного каталога. Готовый исполнитель возвращает позиции исходных строк;
сгенерированная функция make_split не вызывается и больше не требуется.
Split выбирается один раз до экспериментов. При исправлении подготовки запрещено
менять выбранную стратегию, seed и долю validation. Ноды также не могут менять
общий split. Фактически выбранная стратегия записывается
в config['validation'] и сохраняются worker в preparation.json. Если указаны
group_columns, worker проверяет отсутствие общих групп в fit и validation.
Качество выбора идентификатора зависит от условия и подготовки: эта проверка
не обнаруживает автоматически неизвестные связи между строками.

После подготовки роли получают execution_contract: какие этапы завершены,
какие таблицы уже поданы в state и что закреплено. Исходные пути и параметры чтения
исключаются из контекста нод. Общие правила baseline, поиска и реализатора запрещают
создавать повторную загрузку, профиль, внешний split, scorer или writer.
Внутренние фолды/CV на fit разрешены; внешняя validation остаётся общей и без ответов.

## Дерево исследования данных

Исследование включается через research_parallel; по умолчанию 0. До фиксации split
структурная фаза получает признаки без построчных таргетов. После фиксации split
фаза fit получает таргеты только fit. Внешние validation/test таргетов не содержат.

Роль data_researcher возвращает ResearchPlan.analyses: запросы AnalysisRequest с
видом анализа, признаками, популяцией/фильтрами и параметрами. Python-код больше
не генерируется; старые probe.py и цикл исправления исследовательского кода удалены.
Интерфейс analyze_features(state, request) и пакетный run_analyses доступны в
agent/eda.py. Для LLM сейчас используется структурированный JSON-вызов через
ResearchPlan, а не отдельная цепочка нативных tool_calls.

Каталог: quality, association, correlation, shift, groups, redundancy, missingness,
interactions, predictive, permutation, ablation, feature, stability. Оценка моделей
использует внутреннее разбиение fit и указанную метрику. validation=auto сохраняет
групповую/временную политику при наличии необходимых столбцов. Прокси-модель и её
метрика явно помечены; улучшение проверяется затем обычной экспериментальной нодой.
sample_rows, top_k, estimator, seed, filters и comparison_filters задаёт LLM.
Корреляции и MI — измерения зависимости, а не доказательства причинности.

Для новых признаков используются FeatureSpec: арифметика, отношения, signed_log,
индикаторы пропусков, частоты, клиппинг, групповые средние и части дат. Статистики
учатся на fit; при прокси-оценке — только на внутренней обучающей части. Таргеты
нельзя использовать как вход признака. Для произвольной инженерии сохраняются
составные операции экспериментов; принципиально новые преобразования добавляются в каталог разработчиком.

Кеш research/cache привязан к подготовке, фазе и параметрам измерения; название
вопроса не влияет на ключ. Повторная проверка получает сохранённые измерения.
Частичные результаты пишутся после каждого запроса и сохраняются при таймауте
следующего. Ошибка одного запроса возвращается как failed и не становится фактом.
Reviewer получает только измерения, их область и план. Evidence ссылается на точные
ключи. Краткие подтверждённые выводы по ID передаются Baker и выбранным нодам.

Общий дедлайн и API-семафор разделяются с моделями. Локальные лимиты исследования
остаются прежними: до 12 нод, до 24 API-вызовов в пределах доли общего бюджета,
research_timeout на выполнение; три последовательных неудачи останавливают дерево.
Мониторинг показывает план запросов и результаты вместо Python исследования.

## Контракт блока

Block содержит name, source_node, description, requires, provides и operation.
ToolCall в operation содержит kind, parameters, inputs и outputs. Порядок блоков
проверяется по requires/provides. Новые блоки обязаны выбирать зарегистрированную
операцию; они не содержат исходный код от LLM. Система сохраняет JSON настроек
и короткую доверенную Python-обёртку, которая вызывает run_operation.

Каталог: constant, features, preprocess, fit, predict, automl, ensemble. Входы и
выходы можно переименовывать для нескольких моделей и ветвей ансамбля. Исходные
fit/validation/test/preparation/auxiliary не заменяются результатами операций.
Метаданные, манифест и байты модулей входят в хеш исполняемой сборки. При исправлении
фактическая конфигурация обновляется в манифесте и сохраняется локально вместе с исправленным модулем.


## План ноды и необязательные блоки

Baker возвращает Idea с назначением, родителем, изменением и research_ids. Для
полного AutoML-кандидата Idea.automl сразу задаёт исполняемый AutoMLPlan.
Idea.ensemble сразу компилирует объединение готовых прогнозов нескольких нод:
среднее, голосование, правила по признакам, stacking или gating. Планировщик
для этих двух маршрутов не вызывается. Обучаемые объединения используют
сохранённые прогнозы на общем внутреннем holdout без переобучения источников; внешние метки не передаются. Контракты
и ограничения описаны в [operations.md](operations.md). Остальные
идеи планировщик превращает в NodePlan: pipeline, order, reuse и write. Каждый
write-блок выбирает operation. Штатные алгоритмы конструируются по пути класса
из установленной ML-библиотеки и JSON-параметрам; для них нужен интерфейс fit/predict.
Параметры вложенных sklearn-оценщиков задаются через class_path и parameters.

Новая операция требует добавления её реализации в каталог разработчиком. LLM не
может обойти каталог исходным кодом. Готовые библиотеки остаются основой обучения;
например, нейросети доступны через sklearn MLP или AutoGluon NN_TORCH, а новые
специализированные режимы можно добавить без изменения дерева и JSON-протокола.


## Предок ноды и источники модулей

parent_id — основной предок гипотезы: какое направление решения она развивает.
Это не единственный источник кода. У каждого блока есть собственный source_node.

Следовательно, родство гипотез остаётся деревом, а происхождение кода образует
ориентированный граф. Ссылки разрешены только на сохранённые доступные версии,
поэтому сборка не зависит от одновременно изменяемых рабочих файлов других нод.

Контроллер фиксирует хеш каждого источника в start.json. Сборщик читает неизменённый
блок из исходной ноды по проверяемой ссылке. В modules/ сохраняются только новые
или исправленные блоки. Поэтому исходные ноды нужно хранить до удаления всего прогона.
assembly.json фиксирует порядок и фактические хеши блоков;
хеш исполняемого решения включает manifest, wrapper и все модули.

## Исправления

Первая версия конфигурации исполняется без агента-реализатора. Если smoke или
полное обучение завершается ошибкой блока, роль configuration_repair получает
его настройки, ошибку и контракт. Она возвращает только ToolCall с исправленными
параметрами/связями. Нода сохраняется, другие блоки не переписываются. Проверка и
обучение повторяются с новой версией. Лимит --max-config-attempts равен 5 по
умолчанию; старое имя --max-code-attempts сохранено как алиас.

Ошибка не удаляет ранее сохранённый результат. Анализатор видит фактические
tool_configurations, выполненные этапы, ошибки и диагностику выбранных моделей.


## Анализатор и очередь 5+1

По умолчанию есть шесть мест для исполнения нод: пять improve и одно explore.
Improve развивает лучшего доступного проанализированного родителя; explore
проверяет другое семейство или существенно иной подход. Остаток лимита нод может
сократить последнюю группу. Параллельность настраивается --parallel; для N>1
одно место выделяется explore, остальные improve.

После baseline одновременно запускается не более трёх нод (два improve и один explore
при настроенном общем лимите шесть). После первого проанализированного результата,
который лучше baseline по основной метрике, доступны все настроенные места.

Перед планированием ноды резервируются API-вызовы на план, изменяемые блоки и исправления.
Начальная оценка: три запроса на план, один на исправление каждого изменяемого блока и два запасных;
до получения сборки число блоков берётся из change_blocks, минимум один. После плана резерв уточняется
по фактическому числу write_blocks. Первая конфигурация компилируется локально без запроса реализатору.
Резерв общий для всех ролей: потратить его могут только планировщик и реализаторы
соответствующей ноды. Остальные роли используют свободный остаток. Неиспользованный
резерв освобождается при завершении ноды или отказе планировщика. Это оценка расходов,
а не гарантия исправления произвольного числа ошибок. Если расширить резерв под
фактическую сборку невозможно, план отклоняется до запуска реализаторов.
В report.json поле api_budget содержит remaining, free и reserved по нодам;
search_parallel_limit показывает текущий лимит мест. События api_budget_reserved,
api_budget_released и node_budget_wait объясняют решения планировщика.

Как только нода закончилась, контроллер сохраняет её результат и обновляет best.
Затем LLM-анализатор получает все модули этой сборки, контракт, ошибки попыток
и сравнение с baseline, родителем и текущим лидером. Возвращает summary, findings,
next_ideas с указанием относящихся к ним блоков.
Анализатор опирается на status, stage, evaluation_status и value из результата ноды.
Написанный исходник не подтверждает исполнение. Score считается измерением только
при завершённой оценке; промпт явно разделяет намерение кода и подтверждённый результат.
Отладочные журналы, traceback и сохранённые API-запросы в контекст анализатора
не передаются; ошибки исправлений остаются краткими: блок, версия, этап и сообщение.
Анализатор получает отдельные измеренные сведения о входах smoke и полного запуска:
число строк и уникальных значений target. Они привязаны к хешу исполняемого кода.
Статусы и длительности этапов передаются отдельно; заметки реализатора в историю для LLM не входят.
Промпт запрещает переносить факты smoke на полный train и выдавать предположения за измерения.

Baker управляет очередью двумя способами: добавляет до трёх новых идей за вызов
и обновляет уже ожидающие идеи по ID. Он может вернуть меньше идей, пустой список
или только изменения очереди. `priority` задаётся от 0 до 100; первым берётся
наибольший приоритет с доступным местом improve/explore. Равные приоритеты сохраняют
порядок поступления. Размер очереди ограничен числом параллельных мест и остатком
общего лимита нод. Контекст содержит занятые места и лимиты improve/explore.

Ответ `Ideas` содержит `ideas` и `updates`. Обновление задаёт `idea_id`, действие
`prioritize` с новым `priority` либо `remove` и обязательную причину. Менять можно
только ожидающие идеи. Если идею уже забрал планировщик или она выполняется,
обновление пропускается без отмены работы и без отклонения остальных действий.
Решения и причины сохраняются
в `ideas.json` и `planning/batch_*/response.json`; мониторинг показывает порядок,
приоритеты и удаления. Приоритет сам по себе не создаёт новую уникальную идею.

Baker вызывается при нехватке идей, новом завершённом анализе эксперимента или
новой версии контекста исследований, даже когда очередь полна. Одновременно
выполняется один запрос Baker. Обновления, поступившие во время запроса, не
отменяют его ответ: следующий вызов получает их вместе в актуальном JSON.
При неизменном контексте и полной очереди новых вызовов нет. Три ответа без новых
идей приостанавливают пополнение до следующего анализа, сохраняя ожидающую работу.

Пока одна нода обучается, уже может готовиться следующая идея. Планировщик получает
свежий каталог блоков и контекст своего родителя. Его подготовка плана занимает
то же место improve/explore, что и последующее исполнение: вместе их не больше шести.
Готовый план сразу запускает ноду, без ожидания остальных планировщиков.
При смене проанализированного лидера ещё не взятые improve-идеи прежнего родителя
помечаются superseded; уже начатая работа не прерывается. Explore-идеи сохраняются.

Все роли используют один семафор: до 8 обращений к LLM. Ожидание места расходует
общее время, но не API-вызов и не HTTP-таймаут. Для всех ролей действует
LLM_TIMEOUT_SECONDS; 0 означает отсутствие отдельного таймаута запроса.
Оставшееся время всего прогона ограничивает запрос в любом случае.
Профиль LLM_API_PROFILE=standard использует настройки генерации сервера.
При LLM_API_PROFILE=qwen Baker, анализатор и исправление конфигурации запрашивают
thinking с reasoning_effort=medium; остальные роли используют enable_thinking=false.
LLM_TOOLS_ENABLED управляет доступом к справочнику через function calling.
Ответы проверяются по JSON-схеме локально. Настройки: [connection.md](connection.md).

На один ответ — до трёх HTTP-попыток без учёта двух продолжений после справки,
включая не более одного сетевого повтора
и двух невалидных ответов. Пустой или обрезанный ответ запрашивается заново;
при обрезании установленный max_tokens удваивается. После исчерпания этих попыток
пустой/обрезанный ответ остаётся временной ошибкой, которую Baker может повторить
в пределах своего лимита. Валидный JSON с Markdown-ограждением, в том числе без
закрывающей строки, очищается локально без нового запроса. Если Baker вернул лишние
валидные идеи, выбираются допустимые по приоритету до запрошенного числа; updates
сохраняются. Ошибки обязательных полей по-прежнему требуют исправления ответа.
В журнале сохраняются роль,
thinking, finish_reason и полная статистика usage, предоставленная сервером.
После временной ошибки Baker повторяет запрос через 5 секунд. Три неудачных
цикла подряд останавливают генерацию новых идей; активные ноды и готовые идеи
сохраняются. Ошибка одного планировщика освобождает его место и не отменяет
другие планы. На план одной ноды — до трёх HTTP-попыток. На анализ и одну
генерацию блока — до пяти с учётом двух продолжений справки; исправления блоков
используют отдельный настраиваемый лимит версий кода (по умолчанию пять).

HTTP 429 в ролях агента получает до двух повторов в пределах общего лимита
трёх HTTP-попыток на ответ. Повтор сохраняет тот же контекст и не создаёт ноду
или новую версию блока. Пауза из Retry-After (секунды или HTTP-дата) либо
retry-after-ms распространяется на все роли текущего прогона. Без заголовка
используются паузы 5 и 10 секунд. Ожидание расходует время, но не API-вызовы;
каждый фактический повтор учитывается в общем и локальном лимитах.
После исчерпания попыток ошибка остаётся временной для существующего механизма Baker.

Явное сообщение об исчерпанном бюджете/квоте ключа останавливает новые запросы
этого прогона без повторов. В llm/*.response.json и events.jsonl сохраняются
HTTP-статус, категория ошибки, безопасные код/тип провайдера и выбранная пауза.
Полное тело ответа и заголовки авторизации не записываются. Для диагностики
используется категория, а не предположение, что любой 429 означает исчерпанный бюджет.
Формат Retry-After: [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after).

При каждом запуске четыре роли заново извлекают факты из текста задания.
Ответы и извлечения соседних запусков не подгружаются. Хеш текста в отчёте
нужен только для идентификации задания. JSON-схемы и точные цитаты проверяются локально;
принудительный `response_format` серверу не передаётся.

Точные повторы идей отбрасываются до планирования; при этом прогноз, приоритет
и ссылки на исследования не меняют идентичность идеи. После планирования ключ
содержит исходное изменение Baker, pipeline и интерфейсы/источники сборки.
Одинаковые интерфейсы без совпадения изменения не означают одинаковые эксперименты.
Перефразированное описание блока не делает ту же гипотезу новой. Состояния идей, отклонённые планы и ошибки видны Baker при
следующем запросе. Другие идеи продолжают работу независимо от отказа одной.
После трёх пакетов без новых идей Baker ждёт следующего анализа; если другой
работы больше нет, поиск заканчивается с planning_stalled, сохранив лучший результат.
Номера нод резервируются при запуске их планировщиков; неудачный план также
расходует место в общем лимите числа нод и может оставлять пропуск в номерах.

## JSON-контекст

Baker получает до восьми подробных карточек: лидера, свежие результаты и ошибку,
сильные модели разных типов и предков лидера. Краткая таблица сохраняет ID, модель,
статус, качество и время всех нод. Источники прогнозов доступны отдельной компактной
таблицей. В карточке настройки зарегистрированных операций передаются один раз;
фактический результат подбора остаётся в execution_facts.

Архивных инструментов у Baker нет: контекст выбирает Python без дополнительных
LLM-вызовов. Полный журнал, плановые хеши и защита от повторов сохраняются локально.
В прошлых идеях передаются активные работы и до восьми последних отказов; детали
очереди не дублируются. Каталог Baker содержит версии из выбранных нод.

Планировщик получает родителя и до 24 различных версий блоков с приоритетом
запрошенных изменений; все блоки родителя сохраняются, даже если их больше лимита.
Полный локальный каталог остаётся основой проверки ссылок и сборки.
Исправление получает ошибочную операцию, соседние интерфейсы и только выбранные
research_ids. Анализатор получает сохранённую конфигурацию после исправлений,
диагностику и сравнения; Python-обёртки и повторные копии настроек ему не передаются.
Успешный штатный эксперимент анализируется без справочника. Статус выполнения
всегда важнее наличия сохранённого плана или исходника.

Исследователь получает измерительный профиль без второго экземпляра из подготовки,
компактные запросы прошлых проверок и короткую обратную связь моделей. Для Baker и
исследователя выбираются до 12 EDA-выводов, для рецензента — до восьми: сохраняются
ранние наблюдения, свежие выводы и сведения, связанные с текущей работой. Отбор
работает с целыми записями. Тексты не обрезаются по длине. Числовые таблицы рецензента
упаковываются в columns/rows без удаления строк, значений и ключей доказательств.

Повторяющиеся заголовки полей JSON Schema удалены из промпта; имена полей, описания,
ограничения и исходная локальная валидация сохранены. Общие инструкции разделены
по задачам ролей, без дополнительного агента-суммаризатора.

Исходные таблицы не передаются LLM сообщениями. Нативные tool_calls API для этих
операций не требуются: JSON-план один раз передаётся исполнителю. Справочник API
остаётся отдельным инструментом для неизвестных параметров/ошибок.


## Результат и ограничения

Score считает общий Python-scorer. Только контроллер публикует лучший submission;
ошибка или худший поздний результат не заменяют лидера. Метрики разных split
не сравниваются как результаты одного эксперимента.

По умолчанию: 600 секунд на всё, 240 секунд на один полный процесс, 45 секунд
на короткую проверку, до 10 нод вместе с baseline и до 80 API-попыток.
Завершение определяется временем, числом нод, API-бюджетом или отказом планирования.
Сохранённый результат остаётся доступным при поздней ошибке.

Обучение использует fit-часть split. Финального refit на всём размеченном train
после выбора лучшего решения пока нет. Дочерние процессы получают SystemRoot
на Windows и очищенное от ключей окружение. Это ограничение интерфейса и времени,
а не полноценная OS-песочница.

Диагностика не содержит HTTP-заголовков авторизации; текущий API-ключ маскируется.
Сбой записи самой диагностики выводится в stderr и не прерывает работу модели.

Просмотрщик показывает цепочку сборки выбранной ноды, входы/выходы блоков,
источники, изменяемые и исправленные модули. Сплошные связи — parent_id;
пунктирные связи — источники модулей выбранной ноды. По источнику можно перейти
к исходной сборке. Отдельно видны анализатор, его выводы, попытки исправления,
этап выполнения и роли improve/explore. Вкладка «Схема» описывает тот же поток.

Статусы читаются из записанных файлов и не доказывают, что процесс всё ещё жив.
Старые монолитные запуски доступны в том же просмотрщике без преобразования.

## Внешняя оценка тренировочных задач

Пять дополнительных наборов находятся в `data/practice/<dataset>/`; каждый task.md
использует существующий интерфейс решения. Агент выделяет собственную валидацию

Команда export копирует только пять файлов участника; реальную файловую изоляцию

## Локальный справочник API

`ml_reference.py` выбирает небольшие карточки из корневого `ml_reference_data.py`.
Планировщик получает API выбранной идеи до фиксации параметров. Реализатор и
анализатор получают начальную справку и нативные `search_api`/`lookup_api` из
`ml_reference_tools.py`. До двух раундов справки продолжают тот же диалог роли;
ответ возвращается сообщением `tool`, затем LLM выдаёт финальный JSON.
Эти обращения учитываются в общем API-бюджете, но не создают новую ноду и не
расходуют версии кода. Thinking и общий дедлайн сохраняются. Справочник не меняет split, алгоритм гипотезы или измеренные факты.

Сигнатуры и docstring извлечены из установленных версий. Дополнительные kwargs
AutoGluon прочитаны также из валидатора, делегирование XGBoost — из базовых API,
алиасы LightGBM — из нативного движка, настройки LightAutoML — из конфигурации пакета.
Проверенные пояснения с официальными источниками находятся в `ml_reference_notes.py`.
Версия фактов и версия проверки пояснений отмечаются отдельно.

Справочник не объявляет неизвестный kwargs автоматически недопустимым и не доказывает
успешное обучение по исходнику. Полные данные не уходят в промпт: выдача ограничена
12 тысячами символов для планирования и 5 тысячами начальной справки для реализации
и анализа. По запросу доступны до 10 тысяч символов результатов инструментов за раунд. Пересборка, покрытие и команды — в [ml_reference.md](ml_reference.md).

## Контекст ролей

Baker получает одну историю всех экспериментов: полные конфигурации pipeline,
порядок и источники блоков, список переписанных блоков, результаты и анализы.
История не обрезается до последних нод. Каталог показывает входы и выходы
уникальных версий блоков; подробные описания интерфейсов получает планировщик.
Для уже записанного эксперимента история идей передаёт только ID, статус и ссылку
node_id: полное изменение и конфигурация уже находятся в experiments. Ожидающие,
неудачные и отвергнутые идеи сохраняют свой текст, чтобы не предлагать их повторно.
Прошлые expected_effect не передаются: это прогнозы, а результаты исполнения
находятся в experiments. Полные исходные записи остаются в артефактах.

Планировщик получает одну выбранную идею, pipeline родителя и полный каталог
интерфейсов. Другие ожидающие идеи и анализ родителя ему не передаются: выбор
гипотезы уже сделал Baker. Планировщик возвращает pipeline, порядок и спецификации
блоков. В новом pipeline обязательны model.name и model.configuration, а также
непустые текстовые preprocessing и training. Названия и состав алгоритмов свободны;
для ансамбля описываются все модели и способ их объединения. Пустые объекты
не проходят схему. Python преобразует это в сохранённый формат Pipeline с полями
data/preprocessing/model/training; data остаётся пустым, поскольку общая загрузка
уже завершена. Старые сохранённые Pipeline продолжают читаться без подмены их данных.
Python сохраняет rationale, expected_effect и research_ids из исходной идеи. Все названные
в change_blocks модули должны попасть в write. Анализатор сравнивает план и код
с исходным изменением; это не заменяет проверку результата исполнения.

Реализатору нужны его блок, общая сборка, текущий код и ошибка; анализатору —
рассматриваемая нода, исходники, факты запуска и сравнения.
Повторная история model_feedback передаётся только исследователям данных.
Она не дублируется в запросах Baker, планировщиков, реализаторов и анализаторов.
JSON схем и контекстов передаётся без необязательных пробелов.

Анализатору предложено писать новые находки и ограничения с указанием блоков,
не пересказывать уже переданные настройки, размеры, score и длительности. Это
сокращает будущую историю без удаления сохранённых анализов. Настройки thinking,
лимиты времени и число API-вызовов из-за компактного представления не меняются.


## Краткие исследования и выбор контекста

Промпт просит краткий summary, до трёх новых инсайтов и до трёх открытых вопросов.
Для анализов и исследований длина текста и число пунктов — рекомендации краткости,
а не ограничения схемы. Полезный ответ не отбрасывается за превышение длины.
При исправлении JSON предыдущий ответ передаётся целиком. Структура, типы и ссылки
на измеренные факты по-прежнему проверяются.

Полная рецензия и evidence остаются в артефактах. В общий контекст выводов попадают
ID, фаза, observation/interpretation и statement. Рекомендации implication не
дублируются в запросах: экспериментальные действия выбирает Baker. Он получает
все активные краткие факты, но не открытые исследовательские вопросы. В каждой
новой идее Baker указывает research_ids нужных фактов; неизвестные ID отклоняются.
Планировщик, реализатор и анализатор получают только эти факты. Если ссылок нет,
исследовательский контекст не передаётся. Недоступный или пересмотренный ID явно
помечается, а не заменяется выдуманным фактом.

Исследователь получает историю вопросов, фаз, статусов и исходов без повторных
полных review. Измерения представлены компактным профилем: имена сгруппированы
по dtype, квантильные уровни заданы один раз, значения, cardinality и частоты
категорий сохранены. missing/nonfinite содержат ненулевые количества. Такое же
представление profile доступно программе в state; полная версия остаётся на диске.
У структуры нет построчных target, у fit они есть, у validation/test их нет.

Исследователь и рецензент должны проверить сравниваемые популяции, единицы,
знаменатели и доступность нужных ответов. Другая статистика или proxy не выдаётся
за недоступное измерение; повторяемость значений сама по себе не доказывает заглушку
или ошибку данных. Эти правила помогают рецензии, но не являются математическим
доказательством её выводов.

Повтор вопроса в той же фазе отклоняется независимо от гипотезы, регистра,
пробелов и пунктуации. Собственную программу можно исправлять с тем же вопросом.
Перед каждой попыткой обновляются история вопросов/методов, текущие краткие факты
и параллельные работы. Промпт требует сравнивать популяции, признаки, статистику
и предмет сравнения, ссылаться на готовые факты и объяснять новое измерение
для follow-up. Смысловые перефразирования контролируются промптом; точный ключ
не является семантическим поиском. Одинаковые активные statement одного типа
в одной фазе не добавляются в память повторно.

Короткая API-справка отдаёт приоритет выбранным API, методам и упомянутым параметрам.
Общие импорты добавляются в оставшееся место. Адресный lookup_api возвращает
сведения о запрошенном параметре, без повторения всей сигнатуры и главы справочника.
Результаты lookup_api разделяются между ролями одного прогона; релевантные параметры
той же установленной версии заранее включаются в следующие запросы. Память не
переносится между прогонами. Инструменты остаются для отсутствующих деталей;
промпт просит объединять вопросы в один раунд и не подтверждать уже переданные факты.
Пакет ответов инструментов занимает до 5000 символов. Событие api_reference_selected
показывает выбранные API, размер справки и количество повторно использованных параметров.

Общие правила обучения требуют подбирать пороги, калибровку и веса ансамбля по
отложенным или OOF-предсказаниям внутри fit, затем фиксировать настройки до
переобучения на всём fit. Анализатор проверяет, какая модель получила эти
предсказания и видела ли она соответствующие строки при обучении. Настройка
по предсказаниям финальной модели на её обучающих строках считается методической
ошибкой. Это правило и проверка модели, а не универсальный статический валидатор
произвольного ML-кода; внешняя оценка может оставаться корректной.

Обновление исследования данных само по себе не вызывает Baker при заполненных местах
и очереди. Новая справка попадёт в следующий необходимый запрос. При новом анализе
модели Baker может обновить ожидающие идеи без добавления новых.

Успешные ноды анализатор разбирает по коду, измерениям и заранее выбранной справке,
без инструментальных продолжений. При неуспешном результате инструменты доступны.
При первой реализации разрешён один раунд справочника; при исправлении кода — два.
В раунде можно объединить до трёх вопросов. После лимита требуется итоговый JSON.


### Готовые AutoML-кандидаты

После успешного первого baseline поиск один раз ставит в очередь FLAML и
AutoGluon Tabular из ветки max. Они занимают обычные места improve и входят в
общий лимит нод; Baker и реализатор для их создания не вызываются. Для каждого
кандидата сохраняется обычный блок builtin_flaml или builtin_autogluon, поэтому
работают сборщик, мониторинг, общий scorer, выбор лидера и анализатор. Ошибка
адаптера завершает только его ноду; уже сохранённый результат остаётся доступен.

Подбор идёт только внутри fit. Внешняя валидация и тест получают предсказания,
их таргеты недоступны адаптеру. Импорты библиотек отложены до запуска ноды;
предлагаются только установленные движки. Как и в max, готовое портфолио
применяется к одному табличному таргету с известной метрикой без временного или
группового разбиения. Для остальных задач требуется подходящая операция из каталога.
Названия таргетов и признаки публичных датасетов в адаптерах не зашиты.

AutoML соблюдает runtime.deadline и num_cpus; запуск по-прежнему ограничивает
родительский процесс. Выбранный алгоритм/параметры и внутренние оценки пишутся в
*_full_diagnostics.json и поступают анализатору отдельно от внешней метрики.
Baker получает короткий список уже поставленных AutoML-кандидатов, чтобы
продолжать их улучшение вместо повторного запуска того же портфолио.

Автоматически проверяются два движка: FLAML и AutoGluon. Для LightAutoML пока нет
готового адаптера; Optuna настраивает sklearn-совместимые алгоритмы через операцию fit.
Включено по умолчанию; --no-automl отключает готовые кандидаты. Команда baseline
с одной разрешённой нодой по-прежнему запускает только простой предиктор.

### Управление AutoML со стороны Baker

Idea.automl задаёт AutoMLPlan: engine, models, model_parameters, search_space,
num_trials, validation/folds, holdout_fraction, bag_folds/stack_levels (AutoGluon),
ensemble, budget_fraction, columns/drop_columns и features. План сразу превращается
в обычную ноду с сохранённой конфигурацией, без вызова реализатора/планировщика.
Параметры поиска переводятся в собственные домены FLAML/AutoGluon. Внешний split,
scorer и ресурсы воркера планом не заменяются. Smoke использует короткую модель;
полный запуск применяет запрошенные настройки. Одинаковый AutoMLPlan не запускается
повторно из-за нового текста гипотезы или другого родителя.
