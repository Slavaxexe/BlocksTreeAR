# Пайплайны регрессии в этой ветке

**Основной: `autoresearch/`** — сквозной AutoResearch с памятью, честной валидацией по времени, историей объектов
и циклом «гипотеза → эксперимент → урок» с Qwen. Описание: [autoresearch/README.md](autoresearch/README.md).
Точка входа платформы `solution.py` запускает его для регрессии и прежнего агента — для остального.

Ниже — первая интеграция этапов команды (`regression_pipeline.py`: Марго → выбор модели → Макс). Оставлена как
проверенная сборка стыков; её валидация случайная (test же — следующий год), поэтому её метрики завышены.

# Сквозной пайплайн регрессии

```
task.md + csv ─► 0. задача ─► 1. подготовка данных ─► 2. выбор модели и лосса ─► 3. обучение и валидация ─► submission.csv
                 (раннер)      Марго: data_preparation   Виталий: model_selection   Макс: agent/training_*
```

Запуск из корня репозитория:

```bash
uv sync --locked
uv run --locked python regression_pipeline.py data/regression            # с Qwen (ключ в .env)
uv run --locked python regression_pipeline.py data/regression --no-llm   # без Qwen
```

`.env` в корне (в git не попадает): `OPENAI_API_KEY`, `OPENAI_BASE_URL=https://inference.airi.net/v1`,
`OPENAI_MODEL=Qwen/Qwen3.8-27B`. Эти же переменные читают все три этапа и `baseline.py`.

## Этапы и стыки

Каждый этап пишет вход и выход в `artifacts/pipeline_<время>/NN_<этап>/`. Стыки — только через файлы.

| # | Этап | Вход | Выход | Qwen |
|---|---|---|---|---|
| 0 | Понимание задачи (`regression_pipeline.read_task`) | `task.md`, `sample_submission.csv` | `00_task/task.json`: target, id, метрика | нет: target/id из шаблона ответа, метрика — regex по `task.md` |
| 1 | Подготовка данных (Марго) | каталог задачи, target, метрика | `01_preparation/*.parquet` + 5 JSON; склейка в `02_data/{train,test}.csv` | идеи признаков (опционально) |
| 2 | Выбор модели и лосса | `02_data/train.csv`, метрика | `03_model_selection/output.json`: кандидаты (модель, лосс, приоритет, обоснование) | выбор внутри реестра + валидатор, фолбэк — правила |
| 3 | Обучение и валидация (Макс) | `04_training_input/input.json` (контракт `TrainingInput`) | `05_training/report.json`, `submission.csv` | сплит, планы, анализ результатов |

### Адаптер 2 → 3 (`selection_to_training_input`)
- `model_id` → `family` Макса: `hist_gb→hist_gradient_boosting`, `sgd_linear→sgd`; `knn`, `huber_linear` — у Макса
  нет шаблона, пропускаются с предупреждением.
- Лосс передаётся в `selected_models[].parameters` (`objective` / `loss_function` / `criterion` / `loss`):
  бэкенд Макса берёт их как базу, планировщик Qwen может переопределить.
- Трансформ таргета (`log1p`) бэкенд Макса не поддерживает → кандидат откатывается к базовой паре метрики,
  это пишется в предупреждения.
- Метрики этапа 3: `rmse, mae, mse, r2, mape`. Другая метрика (rmsle, pinball) — явная ошибка, а не подмена.

### Без Qwen (`--no-llm`)
- Этап 1 — детерминированный план Марго.
- Этап 2 — дефолт правил (`source: rules_fallback`).
- Этап 3 — `OfflineAgents`: 20% внешний holdout, по одной стартовой конфигурации на модель
  (`OFFLINE_PARAMS`), без дальнейших раундов. Это проверка стыков и нижняя граница качества, а не финальный режим.

## Бюджет времени (лимит платформы 3 ч)
`--total-budget` по умолчанию 10 200 с (3 ч минус 10 мин запаса). Подготовка ≤ 900 с, probe ≤ 300 с,
остаток — этапу обучения; внутри него 25% (≤ 1200 с) зарезервировано на финальное переобучение.

## Метрика без платформы
`pipeline_report.json → metrics`: метрика победителя на внешней отложенной выборке этапа 3, все опыты,
эталон-константа на том же split, проверки submission (число строк, порядок id, конечность).
Балл платформы `S = 100·max(0, 1 − RMSE/B_RMSE)` локально не считается: нужен RMSE бейзлайна организаторов
на их скрытом тесте.

## Что не сделано / известные ограничения
- Этап 0 детерминированный. На приватных задачах с нестандартной формулировкой метрики стоит
  подключить разбор `task.md` через Qwen (`agent.agents.extract_task`).
- Этап 1 кодирует категории one-hot до этапа 2 → CatBoost теряет нативную работу с категориями.
- Трансформ таргета не доходит до этапа 3 (нет поддержки в бэкенде).
- Подготовка данных обучает трансформер на 80% train, а этап 3 делает свой split — для безучительных
  преобразований (медианы, one-hot) это несущественно, таргет в план признаков не входит.
