# Карта проекта

Код компактный и читаемый, без искусственных слоёв и дробления на мелкие модули.
Короткие выражения не растягиваем, длинные не минифицируем. Комментарии объясняют
причины и ограничения. При изменениях обновляем эту карту и архитектуру.

Генерируемый Python хранится внутри запуска. Это не новые исходные модули проекта.
Autopilot (по умолчанию в CLI / `solution.py`): временной / adversarial split при измеренном
сдвиге, `node_000` от контроллера без LLM, Reviewer нод выключен, 4 потока на исполнителя.
Сборщик экспортирует пакет в корневые `alfa_*.py`, включая `alfa_cli.py` вместо
`__main__.py`; `solution.py` и subprocess используют эти плоские модули.
В ZIP нет каталогов. `requirements.txt` копируется без изменений из vendor;
сборщик не входит в архив. Проверка распаковывает ZIP вне репозитория и проходит
полный цикл с HTTP-имитацией, настоящими worker-процессами и только двумя
обязательными переменными платформы: ключом и base URL.
Профиль `solution.py`: 10 500 с, 100 нод, два исполнителя, до 1200 с на процесс;
явные аргументы переопределяют значения. API ждёт до 300 с, ответ до 32 768 токенов.
Вызовы идут без provider JSON-mode; удаляется только внешняя Markdown-обёртка,
после чего обязательны прежние проверки JSON / evidence.
Все роли, включая реализатора, исправления и Reviewer, используют reasoning `none` /
thinking `false`. Температура — 0.
Файл ответа также публикуется рядом с Markdown согласно условию; генерируемые
submission исключены из git. Данные в каждую ноду не копируются.

`solution.py` → CLI baseline → `runner.run()` → extractor’ы → prepare.py через
worker → ревью подготовки → baker → start.json → реализатор → smoke → Reviewer → experiment.py через worker → finish / output.
Start неизменен; finish хранит хеши плана / кода, заметки и этап возможного отказа.
После finish runner вычисляет node delta, обновляет общий delta и best. Baker
получает условие, preparation, код лидера и краткую историю score / статусов /
времени / источников ошибок / заменённых блоков pipeline, без прежних rationale,
полных finish и матрицы сравнений;
возвращает improve лидера и explore альтернативы с отдельным родителем. Их start
сохраняются до реализации. Два исполнителя принимают новые ноды по освобождению,
без ожидания пары. Лимит учитывает очередь и работающие ноды. Последняя порция — один improve.
Исправления после smoke / полного запуска
сохраняют start и расходуют общий для ноды лимит из 20 API-запросов, включая Reviewer и JSON-repair.
Reviewer видит текущий код / pipeline, компактный контракт и smoke; до трёх замечаний,
без истории дерева и переписки. Ответ ограничен 8192 токенами. Точные цитаты проверяются
по исходнику; warnings не блокируют. Результат и хеши видны в JSON-вкладках viewer.
Отказ модели возвращается как непроверенный last_refusal, не стирая ошибку исполнения.
Реализатор получает собственный start, общий код / профиль и контракт входных
DataFrame; от родителя — только pipeline / код. Профиль измеряет missing / distinct.
Без completed baseline (и без ошибки scorer) дерево не развивается:
report.stop_reason=baseline_failed; отсутствие реализации метрики допускает score=null.
`viewer.py` независимо читает известные JSON и два известных исходника; CSV,
.env, API и выполнение кода ему не нужны. Конкретные загрузчик и scorer создаются
под условие; в контроллере не зашиты публичные target / имена файлов / метрики.

Summarizer — детерминированные функции в runner.py, без отдельного модуля / LLM-вызова.
Improve продолжает лидера на момент запроса; без score — последнюю успешную ноду.
Explore может продолжить другую завершённую ветку.
Report сохраняет очередь / исполнителей / planning и привязывает API-попытки к node_id.
Перед принятием плана проверяется точное равенство pipeline с историей и pending:
повтор возвращается Baker с конкретной ошибкой в начале и конце запроса.
`contracts.py` проверяет предложения отдельно; `agents.py` выдаёт корректную часть
ответа сразу, запрашивает только отклонённые роли и после двух одинаковых отказов
меняет задание на новое направление. На порцию остаётся общий лимит 10 API-запросов.
`runner.py` перед каждой попыткой даёт свежую delta,
лидера, pending и бюджет; проверки и сохранённый start используют снимок принятого
запроса. Отказ одной роли не прекращает принятую ветку: новый finish позволяет
продолжить планирование. Дополнительных исходных модулей нет.

Новый интерфейс эксперимента — `fit_model(fit, preparation)` с возвращаемой функцией
`predict(features)`. Worker обучает её один раз, проверяет предсказания на переставленных
подвыборках и одной строке, затем считает метрику общим scorer. Для prediction_scope=batch
subset-проверка отключена по смыслу задачи. Finish содержит вспомогательную диагностику;
Baker видит слабые три класса лидера и двух последних нод, а также дельты к родителю.
Guard закрывает ноду после трёх одинаковых AST / этапов / ошибок; разные исправления
сохраняют бюджет 20. needs_replan передаёт Baker цитированный запрос модели на новый план,
не меняя старый start и не выдавая запрос за доказанную невозможность.
Резерв min(15% бюджета, experiment_timeout, 1200 с) используется для финального refit
выбранного исходника со всеми train. Finish / delta и validation-score не переписываются;
при ошибке finalization сохраняется прежний опубликованный submission. Viewer показывает
needs_replan и finalization.json. Новые runtime-файлы проекта не добавлены.
